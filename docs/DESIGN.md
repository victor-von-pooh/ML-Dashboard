# 設計

ML-Dashboard の今の設計と決まりをまとめる. まだやっていないことは [TODO.md](../TODO.md) に置く.

## 1. 役割と位置づけ

[ML-Found](https://github.com/victor-von-pooh/ML-Found) で行った実験の結果を, ローカルの Web アプリで確かめられるようにする.
TensorBoard に近いが, ML-Found の出力の形を前提にすることで, 学習のコードにログを書く処理を足さなくても, 既にある実験をそのまま一覧にして比べられるようにする.
学習の起動と進み具合の確認, 中断もアプリから行う.

「機械学習を全て GUI 上で行う」アプリ (問題の設定, データの分析, モデルの作成・選定, モデルの学習・評価, 推論の段階に分けて作ることを目指している) のうち, 「モデルの学習・評価」の段階で画面を受け持つ. ライブラリは ML-Found.
将来は, 問題の設定の段階が作ったプロジェクトも同じ形で登録して動かせるようにし, 他の段階の画面と 1 つのアプリにまとめることを目指す.

| リポジトリ | 役割 |
| --- | --- |
| ML-Found | 学習のライブラリ. 実験の結果をディレクトリに残す. ダッシュボードが読む情報 (実験の状態, 進み具合) を機械で読める形で書き出し, 外からの中断を受け付ける |
| ML-Dashboard | 画面と API. プロジェクトを登録し, 実験を読み込んで見せる. 学習のプロセスを起動して管理する |
| ML-Quest | 問題の設定のライブラリ (任意の依存の submodule). 問題の設定から後ろの段階に渡す値 (受け渡し `handoff`) を持つ. ダッシュボードは学習で監視する指標と向きだけを受け取る |
| ML_tester | ML-Found のプロジェクトの例を多く持つ, 別のリポジトリの動作確認の場. 多くの種類の学習で画面を確かめる場合に使える (ダッシュボードはこれを前提にしない. 同梱の `demo` だけで手順書と画面の通しのテストが通る) |

画面, 入力フォーム, 学習のプロセスの管理はダッシュボードで作り, ML-Found には入れない.
ML-Found には, ダッシュボード以外からも使える汎用の仕組みだけを足す.

## 2. 使うライブラリと約束

実験の結果は ML-Found が実験のディレクトリに残すファイルから読み, config の確認と学習の起動には ML-Found のコード (submodule) を使う. 問題の設定から受け取る値は ML-Quest (任意の依存の submodule) の受け渡しを通す (下の「ML-Pathfinder の問題の設定」). プロジェクトの形と実験のディレクトリの形は ML-Found が持つ約束で, ダッシュボードはそれに従う.

使う ML-Found の関数は, config の読み込みと確かめ (`load_config` と `start_experiment` が出力先を作る前に行う確かめ), 任意のファイルの読み込み (`load_task`, `describe_origin`, `load_samples`, `read_policy_spec`), 点群の見本の元の座標への戻し (`original_coordinates`), 記録した軌跡からの方策の見積もり (`estimate_policy_value`), 追加の依存の確かめ (`describe_requirements`) とプロジェクトの環境に入れるものの一覧 (`environment_packages`), Optimizer と Scheduler の登録簿. 任意のファイル (`task.yaml`, `samples/`, `policy/policy.json`) は形の決まりを 2 か所に持たないため ML-Found の関数で読み, `evaluations/` (下の「9. 実験の読み込み」), 表, ログ, `run.json`, `progress.json` は下の表のとおり直接読む.

### 読むファイル

ML-Found の今の出力から, 次のように読み取る.

| 情報 | 読むもの |
| --- | --- |
| 指標の推移 | `history.csv` (列 `epoch`, `train/*`, `valid/*`, `lr`. ML-Found の `trainer.eval_train: true` では, 学習用データを推論モードで評価し直した `train_eval/*` も). 学習中や失敗した実験は `train.log` のエポックごとの指標から作る. `lr_steps.csv` があれば, 更新ごとの学習率も読む. ML-Found の `optimizers` (名前付きの複数の Optimizer) の実験は, 学習率の列が `lr_<名前>` になるので, 列ごとに読んで同じ名前の学習率のグラフに重ねる. 横軸に使える列 (下の「学習曲線の横軸」) も返す |
| config | `config.yaml` (全体), `diff.yaml` (default との差分), `source.yaml` (起動のしかた: 実行したスクリプト, 元にした default と experiment の config, 上書き, モデルの定義の写し `model_spec`. 差分の見出しに元にした default を出し, 一覧の中で違う default が 2 種類以上ある場合は, 一番多いものと違う default を元にした実験の差分の欄に印を付ける (検索にも使える). 書いていない実験と, 読めない `source.yaml` は無いものとして扱う. `model_spec` (ML-Found の docs/FORMAT.md の「source.yaml」) は, 定義の場所 (`path`) と写したか (`status`) を config のタブの起動のしかたの行に出す. `status` は写した (`copied`. `model_spec.yaml` と中身の sha256 の先頭 12 文字を添える) と写さなかった理由 (`missing`, `outside`, `link`, `not_file`, `unreadable`, `too_large`, `invalid`, `write_failed`) を言葉にし (「この設定でもう一度起動」のお知らせと同じ言葉), 知らない値は写していないものとして値のまま添える (ML-Found の約束). 辞書でない `model_spec` と, 文字でない `path` と `status`, 64 文字の 16 進の小文字でない `sha256` は無いものとして読む. `model_spec` が null (config の `model.spec` が無い, 空, 文字でない, 参照を解決できない) の実験と, この欄の無い `source.yaml` (前の ML-Found の実験. 写したか分からない) には出さない (どちらもモデルの定義の写しを持たないので, 出す言葉を増やさないため) |
| ログ | `train.log` (警告とエラーを行ごとに区別) |
| 画像 | 実験のディレクトリの中の画像 (学習曲線, 生成画像など) |
| 未コミットの変更 | `git_diff.patch` |
| パラメータの一覧 | `model_summary.csv` (ML-Found が学習を始めるときに保存). モデルの画面に表で出す (多い場合は先頭の 2000 行) |
| 状態 | `run.json` の状態 (実行中のまま残ってプロセスが無ければ不明). `run.json` が無い実験は, `train.log` の「学習完了」とエラーの行から判定 |
| 進み具合 | `progress.json` (学習中の実験だけ). 学習用データの評価し直し (`train_eval`) の間は, そのエポックの学習を終えたものとして進み具合を求める. 段階 (`stage`) が `epoch_end` の間 (FID など高価な評価) は「検証の終わりの評価中」のように出す |
| 何の実験か | `task.yaml` (任意. ML-Found の `load_task` で読む). 受け持ち, 出力の形と意味, 正解の種類, 正解の出どころの説明の文 (ML-Found の `describe_origin`), 作り方, 元にした実験か重み, データセット |
| データ全体の評価 | `evaluations/<名前>.json` (任意). 表 (`table`) と曲線 (`curve`). テスト用の値と守る指標の判定は一覧と比較にも出す (下の「9. 実験の読み込み」の「一覧と比較の評価」) |
| 見本 | `samples/index.json` と `samples/<名前>/epoch_<番号>.<拡張子>`, `final.<拡張子>` (任意. `load_samples`). 画像, 文, 音, 点群, 領域 (`mask`), その他のファイル (CSV は表で見る) |
| 評価の軌跡 | `trajectories/<名前>.csv` と説明の `<名前>.json` (任意. 強化学習の評価の軌跡を ML-Found の `save_trajectory` で書いた実験だけ). 一覧は説明を直接読み, 方策の見積もりは表を `estimate_policy_value` に渡す (下の「9. 実験の読み込み」の「記録した軌跡からの方策の見積もり」) |
| 方策の一式 | `policy/policy.json` (任意. 強化学習の方策を ML-Found の `export_policy` で書き出した実験だけ. `read_policy_spec` で読む). 観測と行動の空間, 守り, 外れたときの動き, 重みの sha256. 重み `policy/policy.pt` は sha256 を確かめるだけで読み込まず, 配らない |

ML-Found が書く `run.json` がある実験では, 状態, ベストのエポック, 環境の情報をそこから読む.
無い実験でも, 上の表の情報で見られるようにする.

読むファイルの形は ML-Found の約束 (ML-Found の `docs/FORMAT.md`) に従う. 知らない項目は無視する. `run.json` と `source.yaml` の `format_version` が, ダッシュボードの知っている版 (どちらも 1) より新しい場合は, 読める項目だけで表示し, 実験の詳細に「新しい版の ML-Found の出力なので, 一部が正しく表示されない場合がある」と注意を出す.

プロジェクトの実験は, `configs/default/` と `configs/experiment/` の config の `experiment.output_dir` の下を探して見つける.

### ML-Pathfinder の問題の設定

書き出したプロジェクトの一覧のために, ML-Pathfinder の置き場 (環境変数 `ML_PATHFINDER_HOME`. 無ければ `~/.ml-pathfinder`) の `problems/<識別子>/problem.yaml` を読む (ML-Fathom の一覧と同じ置き場). 一覧は ML-Quest が無くても出すので, 読むのは `format_version`, `name`, ML-Quest が書き出したときに記録する `project.path` (絶対パスの文字だけ) に限る.

- 並べるのは, 記録の場所が今あり, `configs/default/train.yaml` を持ち, 登録していないプロジェクト. 同じ場所を記録した問題の設定が複数あれば, 更新の新しい 1 件にする. 並びは problem.yaml の更新の新しい順
- 読めないもの, 問題の設定でないもの, 記録の無いものは並べない (プロジェクトの記録ではないため)
- 読める版は 2 まで (ML-Quest の今の版). それより新しい版は読み違えないように読まず, 一覧の上に理由を出す

学習で監視する指標と向き (下の「10. 学習の起動」の「監視する指標と向き」) は, 同じ置き場の問題の設定を ML-Quest の `load_problem` で読み, 受け渡し `handoff(problem)["training"]` の `monitor` と `mode` (ML-Found の `trainer.monitor` と `trainer.mode` と同じ値) を受け取る. 問題の設定の YAML から値を求め直さない (指標から監視する名前と向きを決める約束は ML-Quest にあるため).

- ML-Quest は任意の依存 (`backend` の extra `problem`. `make setup` は既定で入れる) で, 使うときだけ読み込む. 入っていない場合と `handoff` の無い古い版は, この API だけを 501 (入れ方の案内) にし, 他の画面と API はそのまま動く
- 渡せない問題の設定 (読めない, 新しい版, 機械学習を使わない, 答えがそろっていない, 既製のモデルをそのまま使うので `monitor` が None, 値の形が違う) も, 理由を付けて並べる (選べない理由が分かるように). 並びは problem.yaml の更新の新しい順. 記録したプロジェクトの場所は `handoff` の `project.path` を, ホームを展開してリンクを辿った場所にしたもの (登録したプロジェクトの場所と比べるため)

### 書くもの

実験のディレクトリとプロジェクトのファイルには, 中断の要求 (`STOP`) と, 利用者が「学習の準備」で確かめて始めたプロジェクトの `.venv` (下の「12. 学習の準備」) 以外を書かない. 画面で書き換えた config, ジョブの記録, メモ, タグ, 星はダッシュボードのデータの置き場に書く (下の「6. 置き場」).

### 状態, 進み具合, 中断のやり取り

実験の状態 (`run.json`), 進み具合 (`progress.json`), 中断の要求 (`STOP`) は ML-Found が持つ汎用の仕組みで, 形は ML-Found の `docs/FORMAT.md` にある. どれもファイルでやり取りするので, ダッシュボード以外 (別の端末のスクリプトなど) からも使える. Python のコードから指標を受け取るコールバック (`add_callback`) はダッシュボードでは使わない.

## 3. 画面

1. **プロジェクト**: 登録したプロジェクトの一覧. 実験の数, 最新の実験. 実行中のジョブの数は左のサイドバーの「ジョブ」に出す
    - 「プロジェクトを追加」のダイアログの先頭に, ML-Pathfinder で書き出した, まだ登録していないプロジェクトを並べ, 「登録」を押すだけで登録する (場所を打たずに済むようにするため). その下に, 場所を書いてその下のプロジェクトを探す欄を置く (置き場の外のプロジェクトと, 自分で作ったプロジェクトのため)
2. **実験の一覧**: 1 つのプロジェクトの画面. 先頭に「学習の準備」のカード (データセット, モデルの定義, 学習の環境と, 環境を作るボタン. 下の「12. 学習の準備」), その下に実験の表. 名前, 日時, 状態, 学習時間, ベストの指標, config の主な差分, テスト用の評価の値と守る指標の印 (下の「一覧と比較の評価」). 並べ替え, 絞り込み, 複数を選んで比べる. モデルの定義の候補を並べて起動した実験を見分けるため, 実験の表に「モデルの定義」の列 (定義の名前. 下の「実験のモデルの定義」) を置き, 検索の欄で定義の名前でも絞り込める
3. **実験の詳細**
    - 概要: 状態, ベストのエポックと指標, 学習時間, 乱数シード, デバイス
    - 学習曲線: 指標ごとのグラフ. 学習用と検証用 (と, 学習用データを評価し直した `train_eval/`) を重ね, ベストのエポックと Early Stopping の位置を示す. 値の無いエポックでは線を途切れさせる (欠けたことが分かるように). ただし, 前後のエポックがどちらも値の無い点 (孤立した点) は線を引けないので, 記号で描く. 何エポックかおきにだけ記録する指標 (例: FID を 10 エポックごと) のように, 値のある点が全て孤立した系列 (値のある点が 2 つ以上) は, 値の無いエポックを飛ばして線でつなぎ, 記録した点に記号を付ける. ML-Found の検証の間隔 (`trainer.valid_every_n_epochs`) が 2 以上の実験 (config で判断) の `valid/` と `train_eval/` も同じく描く. 予定の最後のエポックと `fit` の呼び直しの区切りも検証するので, 点が隣り合う場合があり (例えば 7 エポックで間隔が 3 なら, エポック 3, 6, 7), 点の並びからは推測しない (毎エポック検証する実験の nan の欠けをつながないため). こうした系列には, 記録のあるエポックを点で示して間を線でつないだ旨をグラフの下に添える (比較の画面では, そうした実験の名前). 例えば生成の学習で FID を 5 エポックごとに数える `valid/fid` (ML-Quest の骨組みの `trainer.valid_every_n_epochs`) は, 検証したエポックの点だけをつないで描く. グラフの見出しには指標の良い向き (「大きいほど良い」か「小さいほど良い」. 矢印と文字) を添える. 監視する指標は ML-Found の向き (`trainer.mode`. 比較で実験の向きが食い違う場合は推測), その他は指標の名前から推測し (`loss`, `fid`, `chamfer`, `distance` などは小さいほど良い. `fid`, `chamfer`, `distance` は `/`, `_`, `.`, `-` で区切った語として現れる場合だけで, `confidence` や `fidelity` は含めない. `acc`, `recall`, `ndcg`, `mrr` などは大きいほど良く, 並べる課題の `valid/recall_at_k` と `valid/ndcg` は監視が `valid/loss` の実験でも大きいほど良い. 群分けのシルエット係数 `silhouette` と, `/`, `_`, `.`, `-` で区切った語として現れる調整ランド指数 `ari` も大きいほど良い (`variance` は含めない). 分析の画面の推測と同じ表), 推測した向きには「(推測)」と書く. 名前の分かる指標 (下の「指標の日本語の説明」) は, 見出しの名前の横に日本語の説明を添える. 学習率と, 名前から推測できない指標には向きを出さない (取り違えて良し悪しを逆に読ませないため). 横軸はエポックのほかに, 環境のステップ数などの列を選べる (下の「学習曲線の横軸」)
    - 最新 (学習中) と最終の指標: 指標の推移 (`history.csv`, 学習中はログ) の最後のエポックの値. ただし検証の間隔が 2 以上の実験 (config か, 無ければログの「検証の間隔:」の行で判断) では, 検証しないエポックの `valid/` と `train_eval/` が空なので, それらは最後に検証したエポックの値を出す (学習中と, 検証しないエポックで止めた実験で「—」にならないように. この場合, `train/` とはエポックが違う). 間隔が 1 の実験は, 最後のエポックで空 (nan など) の値をそのまま空で出す. ベストのエポックは ML-Found が判定したエポック (`run.json` かログ. 無ければ値のあるエポックから求める) なので, 検証したエポックの中から選ばれる
    - config: 全体と default との差分
    - モデル: モデルの構造, Optimizer, Scheduler (`train.log` から), 名前付きの Optimizer (`optimizers`) の場合は名前ごとのクラス, 受け持つ部分, Scheduler の表 (`run.json` の `optimizers` から. 書いていない版の ML-Found の実験には出ない), Scheduler の主な引数 (`run.json` の `optimizers` の `scheduler_params`. Optimizer が 1 つの実験は Scheduler の欄に, 名前付きの場合は表の Scheduler のクラス名の下に出し, 表を横幅いっぱいにする. 形は ML-Found の docs/FORMAT.md の「Scheduler の引数」. 中の Scheduler (`schedulers`) は中の Scheduler ごとに入れ子にし, `groups` はパラメータグループごとの表, `partial` の関数 (`{function, args, keywords}`) は `partial(関数, 引数, 名前=値)` の形, 並びは `[...]`, `"inf"` などの文字はそのまま出す. 同じ条件で学習し直すときに, 自分で渡した Scheduler の引数も画面から読めるようにするため. 辞書でない値と書いていない版の ML-Found の実験はクラス名だけ). `run.json` の `optimizers` が空のリストの実験 (パラメータの無いモデル. 下の「パラメータの無いモデルの実験」) は, Optimizer と Scheduler の欄に, 学習で更新する重みを持たないので使わないことを出す, パラメータの一覧 (`model_summary.csv` から. 名前か層で検索でき, 学習する, しないパラメータとバッファの要素数を出し, 重みの共有も示す)
    - 環境: git の情報と未コミットの変更, OS, PyTorch, パッケージ
    - ログ: `train.log`. 警告とエラーを強調
    - 画像: 番号の付いた画像のエポックごとの推移 (スライダーと再生), 実験のディレクトリの画像とファイルの一覧
    - 何の実験か (`task.yaml` がある実験だけ): 受け持ち, 出力の意味, 正解の種類と出どころ, 作り方と元にしたもの. 下の「9. 実験の読み込み」の決まりで出す
    - 評価 (`evaluations/` がある実験だけ): データ全体の評価の表と曲線. 守る指標を先頭に. 名前の分かる評価 (ML-Quest の異常の検知の骨組みの `anomaly_<分割>`, `anomaly_scores_<分割>`, `anomaly_top_<分割>`) は, 名前の横に日本語の名前 (「上位 K 件の適合率と PR-AUC」「度合いの分布」「上位の行の要約」) を添える. 異常の検知の評価を持つ実験は, タブの先頭に「異常の検知の評価」の欄を置き, 度合いの決め方, 上位の件数 K, 人が 1 回に確かめる件数の上限 (config の `anomaly.score`, `anomaly.k`, `anomaly.capacity`. 書いていない項目は出さない) と, 評価の読み方 (度合いは行ごとの異常らしさで大きいほど学習用の正常の行から外れていること, 異常の行のある分割は上位 K 件の適合率と PR-AUC, 異常の正解の無い分割は度合いの分布と上位の行の要約, 推論の段階では度合いの高い順に件数の上限まで人の確認に回すこと) を出す (K と件数の上限は評価の説明の文の中にしか無く, 評価と並べて読むため). 同じく ML-Quest の効果の見積もりの骨組みの `uplift_<分割>` と `qini_curve_<分割>` には「Qini の係数と上位 K 割の効果の差」「Qini の曲線」を添え, 効果を見積もるの評価を持つ実験は, タブの先頭に「効果の見積もりの評価」の欄を置き, 上位の割合 K (「上位 30 %」のように % で書く) と配る数の上限 (config の `uplift.k`, `uplift.budget`. 書いていない項目は出さない) と, 評価の読み方 (効果は処置したときの結果からしないときの結果を引いた見積もりであること, 処置の群と対照の群の意味, 正解の効果は顧客ごとには見えず上位の行の処置の群と対照の群の結果の平均の差で数えたこと, Qini の曲線とでたらめに配る線の読み方, Qini の係数と上位 K 割の効果の差はどちらも大きいほど良く全体の効果の差と比べること, 推論の段階では効果の高い順に配る数の上限まで配ること) を出す. 同じく ML-Quest の値段を変える判断の骨組みの `price_<分割>` には「売れた数の予測の誤差と見込みの利益」を添え, 値段を変える判断の評価を持つ実験は, タブの先頭に「値段を変える判断の評価」の欄を置き, 変える割合の候補 (「-10 %, 0 %, +10 %」のように符号を付けた % で書く) と値段を変える幅の上限 (「10 %」のように % で書く. 守る指標) (config の `price.candidates`, `price.max_change`. 書いていない項目と読めない項目 (今の値段の 0 を含まない候補など. 骨組みは 0 を必ず含む) は出さない) と, 評価の読み方 (値段, 売れた数, 原価と今の値段の意味, 売れた数の予測の誤差は記録の値段で数えた予測と記録の差で小さいほど良いこと, 弾力性は今の値段を 1 % 上げたときに予測した数が何 % 変わるかの商品の平均で良し悪しの向きを持たない読み取りの値であること, 変える割合の候補は今の値段に対する割合で上限を超える候補は選ばず今の値段はいつも選べること, 利益は (値段 − 原価) × 売れた数で原価の列が無ければ売上であること, 見込みの利益とその差と比は記録でなく予測した数から数えた見込みで差と比は大きいほど良いこと, 推論の段階では新しい行の値段を今の値段として同じ候補と上限で選ぶこと) を出す (候補と上限は評価の説明の文の中にしか無く, 評価と並べて読むため). 同じく ML-Quest の時間をまたぐ量の判断の骨組みの `demand_<分割>` には「需要の予測の誤差と発注の数の損」を, `demand_levels_<分割>` には「水準ごとの分位点の損失」を添え, 時間をまたぐ量の判断の評価を持つ実験は, タブの先頭に「時間をまたぐ量の判断の評価」の欄を置き, 学んだ水準, 発注に使う水準 τ (品切れの損 / (品切れの損 + 売れ残りの損). 骨組みと同じ式で数え, 2 進の丸めの端数は出さない), 品切れの損, 売れ残りの損, 発注の数の上限 (守る指標) (config の `demand.levels`, `order.shortage_cost`, `order.holding_cost`, `order.max_order`. 書いていない項目と読めない項目 (小さい順でない水準, 0 以下の損, 負の上限. 骨組みはこれらを誤りとして学習しない) は出さず, τ は 2 つの損が読めるときだけ出す) と, 評価の読み方 (商品と発注を決める日の行ごとに先の期間の需要の分位点を予測し τ の分位点から在庫の数を引いた数を発注すること, 需要の平均絶対誤差は 0.5 の分位点の誤差で分位点の損失は全ての水準の平均で水準ごとの値は水準ごとの表にあり, どちらも小さいほど良いこと, 発注の数の損は売れる数を在庫の数 + 発注の数として品切れの損 × 足りない数 + 売れ残りの損 × 余った数を実際の需要で数えた和で, 前の期間と同じ数の発注との差は大きいほど比は小さいほど良いこと, 発注の数は 0 から上限の整数で上限に当たった行の数が多ければ上限が需要に対して小さい見込みであること, 推論の段階でも同じ決め方で発注の数を決めること) を出す (水準, 損と上限は評価の説明の文の中にしか無く, 評価と並べて読むため). 時間をまたぐ量の判断の評価を持つ実験の実験のディレクトリに商品ごとの発注の数の表 (骨組みが書く `demand_orders.csv`. 形は ML-Inference の docs/DESIGN.md の「需要の一式」の「実験の成果物」) があれば, タブの最後に「商品ごとの発注の数」として見本の CSV と同じく先頭の 200 行の表とダウンロードを出す (2 MiB を超えればダウンロードだけ. 評価の表は全体の値なので, 商品と日ごとに決めた数をここで並べて読むため. 評価ではないので一覧と比較の列にしない)
    - 見本 (`samples/index.json` に項目がある実験だけ): 名前ごとに, エポックを選んで画像, 文, 音, 点群, 領域, CSV の表を見る. 領域は凡例を添え, 点群は元の座標と正規化した座標を切り替え, 表は 2 つを横に並べられる. 見本の横に同じエポックの `history.csv` の指標を並べる
    - 方策 (`policy/policy.json` がある実験だけ): 守りの表, 外れたときの動き, 観測と行動の空間, 重みの sha256 の確かめ. 下の「9. 実験の読み込み」の「強化学習の実験」の決まりで出す
    - 軌跡 (`trajectories/` に表がある実験だけ): 軌跡を選び, 決まった形の方策 (一様, 記録で最も多い行動の ε-greedy) と ε, 割引率を選んで方策の良さを見積もる. 下の「9. 実験の読み込み」の「記録した軌跡からの方策の見積もり」の決まりで出す
    - メモ, タグ, 星 (ダッシュボードのデータの置き場に保存)
    - 次の段階への案内 (完了した実験のうち, モデルの定義か推論の一式 (ML-Inference が読む `inference/inference.yaml`) を持つものだけ. 案内を出す判定では, `run.json` の無い実験は推論の一式を持てば完了として扱う. 状態の表示は未完了のまま. 下の「パラメータの無いモデルの実験」): 推論の一式を持つ実験は ML-Provide の「実験の一覧から登録」, それ以外は ML-Provide の「学習の結果から作る」で使うことと, 実験のディレクトリの場所 (コピーのボタン付き. 詳細の API の `path`) を出す (比べて選んだ実験を次の段階へ渡すため). モデルの定義を持たない実験 (異常の検知の距離に基づく度合いのように, 学習用の正常の行から学んだものを成果物にする実験) には, 写したモデルの定義が無いので「学習の結果から作る」と default の config の `model.spec` の注意を出さない
    - この設定でもう一度起動: 実験の起動のしかた (`source.yaml`) を入れた学習の起動の画面を開く (下の「10. 学習の起動」). 起動できない実験はボタンを押せなくし, 理由を出す
4. **比較**: 選んだ実験の曲線を重ね (検証のエポックだけの指標の描き方と良い向きは学習曲線と同じ), config の違う項目, ベストの指標, テスト用の評価の値と守る指標の印を並べる. 実験の見出し (曲線の系列の名前と表の実験の欄) は, 名前と時刻にし, 同じ名前の実験を 2 つ以上選んだ場合は, その名前の実験に月日も足す (日をまたいだ同じ名前の実験を見分け, 図や共有した画面からも何の実験かが分かるように, 名前は必ず出す). 全てのエポックで同じ値の実験は線が完全に重なって下の線が見えないので, グラフの下に重なっている実験を示す. 長さの違う実験は, 横軸を一番短い実験の最後のエポック (横軸に他の列を選んだ場合は, その列の最後の値) に合わせて見られる (長い実験の横軸では短い実験が左端に縮むため). 横軸は学習曲線と同じく選べ, 候補はどれかの実験で横軸に使える列. 選んだ列を横軸に使えない実験は描かず, その実験の名前を曲線の上に出す (黙って消さないため). 2 つ以上の実験にある番号付きの画像の並びは, 同じ番号の画像を横に並べる. 選んだ実験が 2 種類以上の定義 (名前. 同じ名前で中身の違う組は sha256 の先頭 8 文字で分ける. 下の「実験のモデルの定義」) を使う場合は, ベストの指標とテスト用の評価の表を定義で分けて並べ (定義ごとの見出しの下に, その定義の実験を並べる), 曲線の系列の名前にも定義の名前を添える (候補のモデルを比べて選ぶため)
5. **ハイパーパラメータの分析**: 同じ名前の実験で値を変えた config の項目と, ベストや最後の指標の関係 (散布図, 値ごとの表, 結果を大きく動かした項目の順位)
6. **学習の起動**: スクリプトと config を選び, フォーム (ML-Found の登録簿の説明と範囲付き. default が `optimizers` を使う場合は, 名前ごとに Optimizer と Scheduler の欄を並べ, `optimizers.<名前>` を書き換える) か YAML で書き換え, ML-Found で確かめてから起動する (名前, 必須の引数, 範囲, デバイスに加えて, 仮のパラメータで Optimizer と Scheduler を作れるか. 作ってみる確認は, サーバーが GPU のメモリを持ち続けないように cpu で行う). 値の誤りはフォームに表示する. フォームの先頭にはエポック数と検証の間隔 (`trainer.valid_every_n_epochs`. 1 以上の整数) の欄を置く. 検証の間隔の欄には, 間隔で割り切れるエポックと予定の最後のエポックだけ検証してベストモデルを選ぶこと, Early Stopping と ReduceLROnPlateau の patience は検証の回数で数えることを添える. 検証の間隔を知らない版の ML-Found の config (項目が無い) では, この欄を出さない. 続けて計算の精度 (`trainer.precision`. `fp32` (既定) か `bf16` の選択) と勾配の蓄積 (`trainer.accumulate_grad_batches`. 1 以上の整数, 既定 1) の欄を置く. 計算の精度の欄には, bf16 は順伝播と損失を bfloat16 で計算すること, mps では速さが少し上がるだけでメモリを減らすのは勾配の蓄積の方であることを添える (ML-Found の測った目安). 勾配の蓄積の欄には, 貯めた数のバッチの勾配で 1 回更新し, 小さなバッチで大きなバッチと同じ更新にしてメモリを減らすこと, closure を使う Optimizer (LBFGS など) や複数の Optimizer (`optimizers`) では使えないことを添える. どちらも項目を知らない版の ML-Found の config では出さない. その下に監視する指標と向きの欄を置く (下の「10. 学習の起動」の「監視する指標と向き」). 「モデルの定義の候補」の欄でプロジェクトの `models/` の定義を 2 つ以上選ぶと, 同じスクリプトと config で定義ごとに 1 つずつ, 順に学習する (下の「候補のモデルを並べて起動する」). そのプロジェクトに進めている途中のまとまりがあれば, 画面の上に出す (普通の起動は受け付けるが, まとまりの次の候補は学習中のジョブを待つため)
7. **ジョブ**: 実行中のジョブの進み具合 (エポックとバッチの進捗バー, 残り時間の目安), 中断, 終わったジョブから実験の詳細へ移る. 同じスクリプトのジョブを見分けられるように, 進んだエポックと config の違いの要約を出す. 終わったジョブは同じスクリプトと config でもう一度起動できる (画面で書き換えた config は中身を, プロジェクトの config は同じファイルを使い, 起動と同じ確認を通す). 候補のまとまりで起動したジョブは, まとまりごとに並べる (どの定義の何番目か, 待っている候補, 「残りを取りやめる」. 候補のジョブを中断しても次の候補へ進むことを中断のボタンに添える). 終わったまとまりには「候補の実験を比べる」のボタンを置き, まとまりのジョブの実験で比較の画面を開く (並べて起動した後に比べる画面へ迷わず移るため)
8. **追加の依存**: プロジェクトの Python で確かめた, 機能ごとの要るもの, 入っているか, 入れ方のカード (下の「11. 追加の依存」). 学習の起動の画面は, config の `requires` に足りない機能があれば開始のボタンを押せなくし, そのカードを出す

| `POST /api/jobs/{job_id}/rerun` | 終わったジョブと同じスクリプトと config でもう一度起動する |
| `GET /api/registry` | 選べる Optimizer と Scheduler と引数の仕様 (ML-Found の登録簿) |

API を変えたら `make api` で画面の型 (`frontend/src/api/schema.d.ts`) を作り直す.

## 5. 用語

| 用語 | 意味 |
| --- | --- |
| プロジェクト | ML-Found を使うディレクトリ. `configs/default/`, `configs/experiment/`, 学習のスクリプト (`train.py` など) を持つ. 同梱の `demo` も 1 つのプロジェクト |
| 実験 (run) | 1 回の学習. ML-Found が `<output_dir>/<name>/<日付>/<時刻>/` に作るディレクトリ 1 つに当たる |
| ジョブ | ダッシュボードから起動した学習のプロセス. 終わると 1 つの実験として残る |
| モデルの定義 | ML-ModelControl の定義の YAML. プロジェクトの `models/` に置き, config の `model.spec` で選ぶ. ML-Found が実験に `model_spec.yaml` として写す |
| 候補のまとまり | 同じスクリプトと config で, モデルの定義だけを替えて順に学習するジョブの並び. 記録は置き場の `batches/<ID>/` |

## 6. 置き場

既定は `~/.ml-dashboard/` (環境変数 `ML_DASHBOARD_HOME` で変えられる). ダッシュボード自身のデータ (登録したプロジェクト, 起動したジョブの記録と標準出力, 候補のまとまりの記録と候補の config (`batches/<ID>/`), 環境のジョブの記録と出力 (`environments/<プロジェクトの ID>/`), 書き換えた config, メモ, タグ, 星) をここにまとめる.
プロジェクトのディレクトリには, ML-Found が書くものと, 利用者が始めた環境のジョブが作る `.venv` 以外を置かない.
ML-Pathfinder の置き場は読むだけで, 書かない.

## 7. 安全

既定では `127.0.0.1` だけで待ち受ける (他のホストを指定すると警告を出す). 起動ごとのトークン (Cookie かヘッダー) を持つ要求だけを API で受け付け, 他のサイトからの書き込み (Origin が接続先と違うもの) と別のホスト名での接続を断る. 手元のファイルを読めるので, トークンは他の人に渡さない.

- トークンを知る人は学習のコードを起動できるので, 他のホストで待ち受けることは勧めない
- 環境のジョブはネットワークからパッケージを取って入れるので, 画面で動かすコマンドを見せて利用者が「実行する」を押したときだけ始める. API は画面が確かめたコマンドを受け取り, サーバーが今の確かめで作るコマンドと同じ場合だけ動かす (確かめた後に config などが変わった場合は 409). 入れるものはサーバーが ML-Found の登録簿から作り, 要求から任意のコマンドやパッケージは受け付けない. プロジェクトの `ML-Found/` を `-e` で入れる場合はその中のビルドの設定が動くが, 学習のスクリプトを動かすのと同じ信頼で扱う
- 起動の前の確認 (`/validate` と起動の誤りの文) は, 環境変数の参照 (`${oc.env:NAME}`. 入れ子や文字の中も) の値を返さない (環境変数に入れた秘密の値を画面に出さないため). config と差分の値のうち, 環境変数を引くもの (他の項目を介して引くものも) は書いたままの文字で返し, 他の値は解決して返す (フォームで値を使うため). 警告, お知らせ, 誤りの文の中の値は, その参照の書き方 (`${oc.env:NAME}`) に置き換える. 名前を参照で決める場合 (`${oc.env:${n}}`) は解決した config から名前を引く. それでも名前が分からない参照 (名前の一部だけが参照の `${oc.env:pre_${n}}` や `${oc.env:${n}_x}`, 引けない参照など) がある config では, 全ての環境変数の値を置き換える (安全側に倒すため). ただしこの時は 4 文字より短い値を対象にしない (`1` や `.` のような環境変数で文が崩れないため. 名前の分からない短い値は消し残ることがある). 4 文字より短い値は, 前後が英数字でない所だけを置き換える (数の一部を置き換えないため. 例えば値が `1` なら `(1)` の `1` は置き換え, `10` の中の `1` は置き換えない). そのため, 語に埋まった短い値は消し残ることがある. 値に引用符や改行が入る場合, 文が repr の形 (`\n` や `\'`) で値を挙げると消し残る. 確かめそのもの (範囲, デバイス, Scheduler の食い違いなど) は学習と同じく解決した値で行う. 実験の `config.yaml` などは ML-Found が解決した値で保存するもので, この決まりの外
- ファイルを返す API は, 登録したプロジェクトの実験のディレクトリの中だけを読めるようにし, パスの外への移動を拒否する
- 画面が自分で読む実験のディレクトリのファイル (`run.json`, `progress.json`, `model_summary.csv`, `history.csv`, `lr_steps.csv`, `config.yaml`, `source.yaml`, `diff.yaml`, `train.log`. ジョブの `output.log` も) は, 共通の関数 (`core/run_files.py`) で, 普通のファイルだけをリンクを辿らず (`O_NOFOLLOW`) 待たずに (`O_NONBLOCK`) 開き, 開いたものを `fstat` で普通のファイルと確かめてから, ファイルごとの上限 (JSON と YAML は 4 MiB, CSV は 128 MiB, `train.log` は 64 MiB) までだけ読む (`model_summary.csv` と `lr_steps.csv` は中身を 1 つの文字列にせず行ごとに流して読み, 開いた後に伸びて上限を超えても止める). リンク, FIFO などの普通でないファイル, 上限を超えるファイルは無いものとして読まない (実験の外を読まず, 画面が止まらず, 記憶を使い切らないため). `output.log` は末尾だけを読むので上限を確かめない. `O_NOFOLLOW` の無い環境では, `lstat` で確かめたファイルと開いたファイルが同じかも比べる
- 止める要求の `STOP` は, 同じディレクトリの一時ファイルに書き終えてから `os.replace` で置く. 先にあるもの (リンク, FIFO, 普通のファイル) は開かずに名前ごと置き換わる (リンクの先や, ハードリンクで共有した外の中身を書き換えないため. 書きかけの空の `STOP` を学習が読み, `now` の要求をエポックの区切りの要求と取り違えないため). `STOP` という名前のディレクトリがあれば置かない. `task.yaml` と `samples/index.json` は ML-Found (`load_task`, `load_samples`) が同じく普通のファイルだけを上限までリンクを辿らずに読む
- 見本の一覧 (`samples/index.json`) に書かれたパスも同じ確かめを通し, `samples/` の外を指す項目は出さない. `task.yaml`, `evaluations/` とその中のファイル, `samples/` と `samples/index.json` も, シンボリックリンクなら読まない (実験のディレクトリの外を読まないため). 方策の一式の重み (`policy/` の中のチェックポイント) は返さない. 実験のファイルは, 画像と音はそのまま, 文字のファイルは `text/plain`, それ以外はダウンロードの形で返し, どれにも `sandbox` の Content-Security-Policy を付ける (実験のファイルの中のスクリプトに API を呼ばせないため)

## 9. 実験の読み込み

`task.yaml`, `evaluations/`, `samples/`, `policy/policy.json`, `trajectories/` (ML-Found の約束で任意のファイル) は, 実験の詳細の本体とは別の API (`/results`) で読む.

- どれも無い実験では ML-Found を読み込まず, 何の実験かの欄, 評価, 見本, 方策, 軌跡のタブを出さない
- 読むのは ML-Found の関数 (`load_task`, `describe_origin`, `load_samples`). 形の決まりを 2 か所に持たないため. PyTorch も読み込むので, ファイルがある実験を初めて開いたときだけ読み込む. 読み込めない環境では, 注意を出して他の表示を続ける
- `evaluations/` は, ML-Found の `load_evaluations` が読まなかったファイルとその理由を返さないので, `load_evaluations` と同じ読み方 (名前の順の `*.json` の JSON の辞書. `.` で始まる一時ファイルと読めないファイルは飛ばす) をダッシュボードで行い, `load_evaluations` と同じく, リンク, 普通でないファイル, 20 MiB を超えるファイルを読まない (実験のディレクトリの外を読まず, 止まらないため). 上限の値は ML-Found の公開の `MAX_EVALUATION_BYTES` を使う (値を 2 か所に持たないため). 上限での扱いと読まない決まりが `load_evaluations` と同じことは, 上限のちょうどと 1 バイト超えのファイル, リンク, FIFO を置いて両方で読むテストで確かめる (読み方は 2 か所にあり, 片方だけを変えると食い違うため). 確かめてから読むまでに置き換えられても同じにするため, `evaluations/` を `O_NOFOLLOW` で開いた `dir_fd` から, ファイルを `O_NOFOLLOW` と `O_NONBLOCK` で開き, 開いたものを `fstat` で普通のファイルと確かめ, 上限 + 1 バイトまでだけ読む. `O_NOFOLLOW` や `dir_fd` の無い環境では, 初めに `evaluations/` の (デバイス, i-node) を取ってファイルごとに比べ, `lstat` で普通のファイルと確かめてからパスで開き, 開いたものと `lstat` の (デバイス, i-node) が違えば読まない. 実験のディレクトリより上の入れ替わりは確かめない (他のファイルの読み方と同じ前提). 形 (名前, 列, 行) と名前の確かめは評価のタブと一覧で同じ関数を使い, 名前が ML-Found の決まり (英数字と `_`, `.`, `@`, `-`. 先頭は `.` 以外) に合わないか, ファイルの名前 (`.json` を除く) と違う評価 (ML-Found は名前のファイルに書くので, 写し間違いか手で置いたもの. 同じ名前が 2 つ出ないため) は, どちらにも出さない. ただし大文字と小文字だけが違い, 同じファイル (デバイスと i-node が同じ) を指す名前は同じとみなす (大文字と小文字を区別しない置き場で, 違う大文字と小文字の名前で書き直した場合. ファイルの一覧に `<name>.json` が別にあれば同じとみなさず, 同じ名前を 2 回出さない). 出さないファイルは, ファイルの名前と理由 (シンボリックリンク, 普通のファイルでない, 大きすぎる, 読めない, JSON の辞書でない, 形が違う, 中の name がファイルの名前と違う, 名前が決まりに合わない) を 10 個まで注意に出す (どれをどう直せばよいかが分かるため). 名前は, 制御文字などの種類 (UTF-8 にできない文字, 向きの変わる文字を含む) を `\uXXXX` (BMP の外は `\UXXXXXXXX`) にし, 書き換えた文字の途中で切らずに 80 文字で切る (応答を作れなくならず, 読み違えないため). `evaluations/` 自体がリンクの実験は読まず, 評価の無い実験と見分けられるように注意を出す
- 新しい版の `task.yaml` は, `load_task` が正解の出どころを分からないものに置き換えるので, 出どころを「分からない (新しい版)」と出す (他の欄は読める項目だけを出す). 版が整数でないなど読めない `task.yaml` は, 無いものとして注意を出す
- 正解の出どころが今ある処理 (`process`) なら, 「この処理との一致を測り, この処理を超えられない」を処理の名前と設定と一緒に目立たせる. 他の種類は `describe_origin` の文を出す
- 元にした実験 (`base.experiment`) は, 登録したプロジェクトのどれかの実験のディレクトリなら, その実験の詳細へのリンクにする. 無ければパスの文字のまま. 元にした重み (`base.weights`) は名前のまま
- 評価は, `kind` が `curve` で横軸の列 (`x`) を列に持つものを曲線, それ以外 (`kind` が `table`, 知らない値, 横軸の列の無い曲線) を表として出す (返す `kind` もこの決め方にし, 一覧の列と守り付きの評価の割合も同じ `kind` で決める). 評価の表は列の順に並べ, 向き (`better`) のある列は見出しに「小さいほど良い」か「大きいほど良い」を添え, 値の無い欄 (`None`) は「—」にする (例えば ML-Quest の表の生成の骨組みの `column_distance_valid` の, 種類の列の `wasserstein`). 比べる相手との差の列 (`<指標>_diff` で, `<指標>` の列も表にあるもの) は, `better` に向きがあれば一覧と同じく符号と良し悪し (色とアイコンと「良い」か「悪い」の文字. 0 は「同じ」) を添える (例えば ML-Quest の並べるの骨組みの `ranking_valid` と `ranking_test` の, 人気順との差 `recall_at_k_diff` と `ndcg_diff`. 人気順の値 `<指標>_baseline` は数だけ). ML-Quest の群分けの骨組みの `group_stability` (調整ランド指数の平均 `ari` と最も低い値 `ari_min`, シルエット係数 `silhouette` の, 列の特徴をそのまま k-means で分けた群との差) も同じく印を付け, 群ごとの行の `group_summary` は表のまま出す. ML-Quest の異常の検知の骨組みの評価は, 異常の行のある分割の 1 行の表 `anomaly_<分割>` (`rows`, `anomalies`, `k`, `precision_at_k`, `average_precision`. 向きは 2 つの指標が `higher`), 異常の正解の無い分割の度合いの分布の曲線 `anomaly_scores_<分割>` (横軸 `quantile` と度合い `score`) と上位の行の要約 `anomaly_top_<分割>` (度合いの高い順の K 行. `rank`, 行の id の列, `score`, `column`, `column_share`) を, どれも表と曲線のまま出す. ML-Quest の効果の見積もりの骨組みの評価は, 分割ごとの 1 行の表 `uplift_<分割>` (`rows`, `treated`, `control`, `k`, `qini`, `uplift_at_k`, `effect`, `estimated`. 向きは `qini` と `uplift_at_k` が `higher`. `k` の欄は「上位 30 %」のように % で書く) と Qini の曲線 `qini_curve_<分割>` (ML-Found の `qini_curve` の列. 横軸 `fraction`) を出す. Qini の曲線は Qini の値 `qini` とでたらめに配る線 `random` (破線) だけを描き, 上位の行の数 `rows` は描かない (目盛りが違い, 横軸の割合と同じことを件数で書いた列のため. 表で見る). 系列の名前は日本語の名前に英字の名前を添える. ML-Quest の値段を変える判断の骨組みの評価は, 分割ごとの 1 行の表 `price_<分割>` (`rows`, `products`, `mae`, `rmse`, `elasticity`, `elasticity_counted`, `profit`, `current_profit`, `profit_gain`, `profit_ratio`, `changed`, `max_change`. 向きは `mae` と `rmse` が `lower`, `profit_gain` と `profit_ratio` が `higher`) を出す. 表の `profit_ratio` (選んだ値段と今の値段の見込みの利益の比) と `max_change` (変える割合の絶対値の上限) の欄は % で書く (1.0342 は 103.42 %, 0.1 は 10 %. 比は 1 に近い値の違いが見えるように小数第 2 位まで). ML-Quest の時間をまたぐ量の判断の骨組みの評価は, 分割ごとの 1 行の表 `demand_<分割>` (`rows`, `products`, `mae`, `pinball_loss` (全ての水準と行の分位点の損失の平均), `order_cost`, `baseline_cost`, `order_cost_saving`, `order_cost_ratio` (前の期間の損が 0 なら空), `capped`, `level`, `max_order`. 向きは `mae`, `pinball_loss`, `order_cost`, `baseline_cost`, `order_cost_ratio` が `lower`, `order_cost_saving` が `higher`) と, 分割ごとの水準の数の行の表 `demand_levels_<分割>` (`level`, `loss`. - 見本は名前ごとにまとめ, エポックを選んで見る (null と `final` は「学習の後」). 画像は `<img>`, 文は文のまま (先頭の 2 万文字), 音は `<audio>`, 点群はダウンロードと, ascii の PLY なら上から見た 2D の点 (2 万点まで間引く), 領域 (`mask`) は色分けした PNG と凡例, CSV のファイル (`.csv`) は表 (下の「表の見本」), その他はダウンロード. 説明 (`caption`) と分割を添える
- 表の見本: パスが `.csv` で終わる `file` か `text` の見本 (ML-Found は `.csv` のファイルを `file` で書く. 例えば ML-Quest の表の生成の骨組みの, 作った表 `generated` と見比べる検証用の本物の表 `valid_real`) は, 画面が実験のファイルを文字で読み, 頭の行を列の名前にした表で出す (2 MiB を超えるファイルは読まず, ダウンロードと, 大きいので表にしていないことを出す. 出すのは先頭の 200 行で, 行と列の数を添える). CSV は RFC 4180 の引用符 (値の中の区切りと改行, 2 つ続けた引用符) を読み, 空の値は「—」, 数だけを持つ列 (空の値は除いて見る) は右に寄せる. 最後の見本が表である名前が 2 つ以上あれば, 見本のタブの先頭に「表の見本を並べる」を出し, 「左の表」と「右の表」で選んだ名前の, 最後のエポックの見本を横に並べる (開いたときは先頭の 2 つ). 並べた表は列を左の表の順に揃え, 右の表だけにある列を後ろに足す (作った表と本物の表で同じ列が横に揃うように. 片方の表に無い列は「—」)
- 見本と同じエポックの評価: 見本のカードの中で, 選んだ見本のエポックの `history.csv` の行 (再開で重なる場合は最後の行) を, 指標ごとの行と学習用 (`train/`), 学習用 (評価し直し) (`train_eval/`), 検証用 (`valid/`), その他の値 (学習率など. 接頭辞の無い列) の列の表にして, 見本の横に並べる (カードが狭ければ下). 行の引き方 (エポックごとの最後の行) と列ごとの最も良い値は, 見本のタブで 1 回だけ作り, カードで使い回す. 見本の良し悪しと数字を 1 つの画面で見比べるため. 見本の種類によらず同じ欄で, エポックの選び方は見本のものをそのまま使う (学習曲線の横軸の選択とは別. 表は常にエポックで引く). 指標の向きは学習曲線と同じ決め方 (監視する指標は ML-Found の向き, 他は名前から推測) で添え, 監視する指標の行には「監視する指標」を付ける. 監視する指標の値には, 見本のエポックが `run.json` のベストのエポックのときだけ「ベスト」を付ける (学習曲線のベストの印と食い違わないように. 値が最も良くても, モデルに選ばれなかったエポックには付けない). 監視しない列は, 名前から向きを推測できれば, エポックごとの最後の行の中で最も良い値に「最良 (推測)」を付ける (推測した向きによる印であることを明かすため). 見本のエポックが `run.json` のベストのエポックなら見出しに「ベストのエポック」を, そうでなければ「ベストはエポック N」を添え, 脚注でどちらもモデルに選ばれたエポックを指すと書く. 検証の間隔を空けた実験 (`trainer.valid_every_n_epochs` が 2 以上) で `valid/` と `train_eval/` の値の無いエポックは「検証なし」とし, 間隔を添える (記録が欠けたのか, 検証しなかったのかを分けるため). それ以外の値の無い列は「—」. 学習の後の見本 (エポックが null) はどのエポックの重みで作ったかが分からないので, 指標を並べない旨と, 最後のエポックの監視する指標と検証用の値が上の「最終」の欄にあることだけを出す. `history.csv` にそのエポックの行が無ければ, そう出す
- 領域の見本の凡例は, 一覧の番号の表 (`classes`) の番号, 名前 (無ければ「名前なし」), 色 (PNG の色そのもの. 画面の色の変数でなく, 絵と同じ色にするため) を番号の順に並べる. `classes` が null の見本は絵だけを出す
- 点群の見本の点は, バックエンドが PLY を読み, 一覧の値の決まり (`convention`) を ML-Found の `original_coordinates` に渡して元の座標に戻して返す (`/samples/cloud`. 戻し方の式を 2 か所に持たないため). 値の決まりに `scale` か `shift` がある見本は, 正規化した座標 (ファイルのまま) と元の座標を切り替えて見られ (開いたときは元の座標), 元の座標の軸に単位 (`units`) を添える. `scale` も `shift` も無い見本はファイルのままの座標だけを出し, `units` があれば軸に添える. 知っている版より新しい見本の一覧の項目 (`load_samples` の `newer_version`) は値の決まりを読まないので, 元の座標に戻せないことを出してファイルのままの座標を出す. 求める見本は一覧の `kind: point_cloud` の項目のパスに限る. 読むのは 20 MiB までの ascii の PLY (頂点の要素が先頭で, `x`, `y`, `z` を持つもの) だけで, それ以外は読めない理由を返し, 画面はダウンロードだけを出す
- `samples/` の直下の番号付きの画像 (`samples/epoch_010.png`. `load_samples` が `legacy: true` で返すもの) は見本のタブに出さず, 画像の推移のタブだけで見る (2 か所に並べないため). 名前ごとのディレクトリの番号付きの画像 (`samples/<名前>/epoch_0005.png`) も, 画像の推移のタブに名前ごとの並び (`samples/<名前>`) として出る. 見本のタブは, 同じ画像をエポックを選んで説明と一緒に見る場所
- 一覧の `file` は, 実験のディレクトリの他のファイルと同じ確かめ (`..`, 絶対パス, シンボリックリンクを拒否) で `samples/` の中のファイルに限る. 外を指す項目と無いファイルは出さず, 数を注意に出す

### 一覧と比較の評価

実験の一覧と比較には, データ全体の評価のうちテスト用 (`split` が `test`) と全ての行 (`split` が `all`) の値を列に出し, 守る指標が比べる相手より落ちた実験に印を付ける. 検証用の評価はモデルを選ぶのに使ったので, 候補を比べる値はテスト用にそろえる. 群分けのように正解が無くテスト用に分けない課題は, 全ての行で数えた評価で比べる (例えば ML-Quest の群分けの骨組みの `group_stability`. 群の数 `group.k` を変えた実験を, 群の安定性とシルエット係数の, 列の特徴をそのまま分けた群との差で並べる. 群の数は config の差分に出る). 異常の検知は, ML-Quest の骨組みが異常の行のあるテスト用の行で数えた `anomaly_test` の上位 K 件の適合率と PR-AUC で, 度合いの決め方の違う実験 (自己符号化器と距離に基づく度合い) を並べる. 異常の正解の無い実験 (正解の無い表) は, 骨組みが度合いの分布と上位の行の要約 (曲線と行が 2 つ以上の表) だけを書くので, 1 つの値に決められず一覧と比較の列を持たない (評価のタブで見る). 効果を見積もるは, ML-Quest の骨組みがテスト用の行で数えた `uplift_test` の Qini の係数と上位 K 割の効果の差で, 設定の違う実験を並べる (Qini の曲線は列にしない). 値段を変える判断は, ML-Quest の骨組みがテスト用の行で数えた `price_test` の売れた数の予測の誤差 (`mae`, `rmse`. 小さいほど良い) と見込みの利益の差と比 (`profit_gain`, `profit_ratio`. 大きいほど良い) で, 設定の違う実験を並べる (弾力性は向きを持たない読み取りの値なので, 列には出るが良し悪しで並べる値にしない). 時間をまたぐ量の判断は, ML-Quest の骨組みがテスト用の行で数えた `demand_test` の需要の予測の誤差 (`mae` と全体の分位点の損失 `pinball_loss`. 小さいほど良い) と発注の数の損 (`order_cost` と比 `order_cost_ratio` は小さいほど, 前の期間と同じ数の発注との差 `order_cost_saving` は大きいほど良い) で, 設定の違う実験を並べる. 水準ごとの分位点の損失 `demand_levels_test` は水準の数の行の表なので, 1 つの値に決められず列にしない (全体の値は `demand_test` の `pinball_loss`. 水準ごとの値は評価のタブで見る). 上限に当たった行の数 `capped` は守る指標 (発注の数の上限) に当たった数で, 骨組みは比べる相手との守る指標の表 (`guard`) を書かないので, 落ちた実験の印は付けず向きの無い列として出す (上限に当たるのは需要の大きさにもよるので, 少ないほど良いと決めない). 比較の画面の表の見出しは「テスト用の評価 (群分けは全ての行で数えた値)」. 判定はバックエンドで行い, 一覧と実験の詳細の本体 (比較が読むもの) に入れる.

- 読み方は評価のタブと同じ (上の `evaluations/` の読み方. 読むのはダッシュボードで, ML-Found は上限の値を読むときに限り読み込む). 一覧は全ての実験を毎回読むので, `evaluations/` の中のファイルの名前, i-node, 大きさ, 更新の時刻, 種類と権限, 状態の変更の時刻 (chmod で読めるかが変わるため) と, 向きに使う監視する指標が変わらなければ, 前に求めた値と判定を使う (`train.log` や `model_summary.csv` と同じ覚え方). 覚えた結果は, 一覧を読むたびに, 実験のディレクトリか `evaluations/` が無くなった実験の分を捨てる (消した実験の分が残り続けないため). テスト用と全ての行でない評価は形 (名前, 列, 行) だけを確かめて行を作らない (`split` を先に見る. 出さない評価の行を作る分を省くため). 名前の合わない評価, 形の違うファイル, 読めないファイルは出さず, 上の注意を表の上に出す (一覧では, 注意のある実験の数と, 開くと実験ごとの注意). 数にできない値 (文字, 真偽値, nan, float にできない大きな整数) は無いものとする
- 列にする値: 1 行の表 (`kind: table` で行が 1 つ. データ全体の値) の数の列. 比べる相手との表の形 (`<指標>_diff` の列を持つ表) では `<指標>` と `<指標>_diff` だけにし, `<指標>_baseline` と他の列 (比べた行の数など) は出さない (相手の値は差から分かり, 列を増やさないため). 行が 2 つ以上の表 (グループごと) と曲線は列にしない (1 つの値に決められないため. 評価のタブで見る). 1 つの実験で 100 個まで
- 列の名前は `<評価の名前>:<列>` (評価の名前に `:` は入らない). 並びは守る指標の表を先に, 次に評価の名前, 表の列の順
- 列が多すぎる場合: 一覧には 3 列, 比較には 6 列まで並べ, 「評価の列」の欄 (名前で探せる) で選び替える (表の幅を保つため). 選んだ列は URL に残し, 一覧から比較に移るときも引き継ぐ. 選んでいなければ先頭の列 (守る指標の表が先) を, 向きの分かる列を先にして並べ (行の数や K のような向きの無い列で幅を埋めないため. 例えば `anomaly_test` は上位 K 件の適合率と PR-AUC を, 行の数, 異常の行の数, K より先に. `uplift_test` は Qini の係数と上位 K 割の効果の差を, 行の数と群の行の数より先に. `price_test` は売れた数の平均絶対誤差, 二乗平均平方根誤差, 見込みの利益の差を一覧に, 見込みの利益の比も比較に, 行の数と商品の数より先に. `demand_test` は需要の平均絶対誤差, 分位点の損失の平均, 選んだ発注の数での損を一覧に, 前の期間と同じ数の発注での損と損の差と比も比較に, 行の数と商品の数より先に), 全て外せば並べない
- 指標の向き: 評価の `better` (列ごとの向き. `accuracy_gap` は小さいほど良いため. 変化検出の `change_detection_f1` のように普通の名前に使う語は入れない) を含まなければ, その向きにする. `top1` や `top5` は修飾の語なので表に入れない (向きは `acc` か `err` で決まる). 異常の検知の上位 K 件の適合率 `precision_at_k` と PR-AUC `average_precision` は, `better` が無くても `precision` の語で大きいほど良く, 行の数 `rows`, 異常の行の数 `anomalies`, `k` は向きを付けない. 効果を見積もるの Qini の係数 `qini` は, 骨組みが `better` に書き, 書いていなくても `qini` の語で大きいほど良い (学習曲線の `valid/qini` も). 上位 K 割の効果の差 `uplift_at_k` は骨組みが `better` に書いた向きで読み, 名前の語では向きを決めない. 処置の群と対照の群の行の数 `treated`, `control`, 全体の効果の差 `effect`, 効果の見積もりの平均 `estimated` は向きを付けない. 値段を変える判断の売れた数の誤差 `mae` と `rmse` は, 骨組みが `better` に書き, 書いていなくても名前の語で小さいほど良い (学習曲線の `valid/mae` も). 見込みの利益の差 `profit_gain` (`gain` の語を含むので名前の語では向きを決めない) と比 `profit_ratio` は骨組みが `better` に書いた向きで読む. 弾力性 `elasticity` とそれを数えた商品の数, 見込みの利益 `profit` と `current_profit`, 行と商品の数, 値段を変える商品の数 `changed`, 上限 `max_change` は向きを付けない. 時間をまたぐ量の判断の `mae`, `pinball_loss`, `order_cost`, `baseline_cost`, `order_cost_ratio` と `order_cost_saving` は骨組みが `better` に書いた向きで読む (書いていなくても `order_cost_saving` 以外は `mae`, `loss`, `cost` の語で小さいほど良い. 損の差 `order_cost_saving` は `cost` の語を含むが大きいほど良いので, `saving` を向きを変える語に入れ, 名前の語では向きを決めない). 上限に当たった行の数 `capped`, 水準 `level`, 上限 `max_order`, 行と商品の数は向きを付けない. 両方を含む名前とどちらも含まない名前は, 実験の監視する指標 (`run.json` か config の `monitor` の, 最後の `/` の後) と同じ名前なら, その向き (`mode`) にする. それ以外は分からないとし, 色と印を付けない (取り違えて良し悪しを逆に見せないため)
- 指標の日本語の説明: 名前の分かる列は, 列の見出し (評価のタブの表, 一覧, 比較) を日本語の名前にし, 英字の名前を小さく添える (「評価の列」の欄は英字の名前の下に日本語の名前). 詳しい説明は見出しの `title` に置く. 向きの分かる列 (下の「指標の向き」) は, 一覧と比較の見出しにも評価のタブの表と同じく「小さいほど良い」か「大きいほど良い」を添える (並べ替える前に良い向きが分かるように). 調整ランド指数の平均 `ari`, 最小 `ari_min`, シルエット係数 `silhouette`, 上位 K 件の適合率 `precision_at_k`, PR-AUC `average_precision`, Qini の係数 `qini`, 上位 K 割の効果の差 `uplift_at_k` は名前で引き (学習曲線の `valid/precision_at_k` と `valid/qini` なども), `<指標>_baseline` と `<指標>_diff` は指標の日本語の名前に「(比べる相手の値)」か「(比べる相手との差)」を添える. 群の数 `k` や行の数 `rows` のように評価で意味の変わる列は評価の名前で引く (`group_stability` の `k`, `method`, `repeats` と, `group_summary` の `group`, `rows`, `share`, `stability`. 並べる課題の `k` は並べる件数なので, 評価の名前を見ずに群の数としない). 異常の検知の評価は名前の形で引く (`anomaly_`, `anomaly_scores_`, `anomaly_top_` の後に `_` を含まない分割の名前が続く名前. `anomaly_scores_test` を `anomaly_<分割>` と取り違えないため). 効果を見積もるの評価も同じく `uplift_` と `qini_curve_` の後に `_` を含まない分割の名前が続く名前で引く (Qini の曲線の `qini` は係数でなく曲線の値なので, 評価の名前で引き分ける). 値段を変える判断の評価も `price_` の後に `_` を含まない分割の名前が続く名前で引く (`mae` と `rmse` は売れた数の誤差の意味なので, 他の評価と学習曲線では引かず英字の名前のまま). 時間をまたぐ量の判断の評価も `demand_` と `demand_levels_` の後に `_` を含まない分割の名前が続く名前で引く (`demand_levels_test` を `demand_<分割>` と取り違えないため. `mae` は需要の誤差の意味なので, 他の評価と学習曲線では引かない). 学習曲線と比較のグラフの見出しは, 指標の名前 (最後の `/` の後) の横に日本語の名前と説明を添える. 知らない名前は英字の名前のままにする (取り違えた説明を出さないため)
- 差の色分け: `<指標>_diff` の列は, 向きが分かれば, 良い差を `--good-text` と丸の印と「良い」, 悪い差を `--critical-text` と三角の印と「悪い」, 0 (と, 計算の誤差の幅 1e-12 の中) を「同じ」と出す. 向きの分からない差は値だけを出す
- 守る指標の印: テスト用と全ての行の守る指標の表 (`guard: true`. 行が 2 つ以上の表も) の全ての行の `<指標>_diff` を (上の向きで) 見て, 1 つでも悪い向きの差なら「落ちた」(`--critical-text` と盾の注意の印), 全て判断できて落ちていなければ「保った」(`--good-text` と盾の印), 差の列が無い, 向きが分からない, 値が無いものが残れば「判断できない」(色を付けず, 盾の問いの印) とする. 差が 0 (と, 計算の誤差の幅 1e-12 の中) は落ちていないとする. 印の説明に, 落ちた指標と一番悪い差, 判断できなかった理由を出す. 印はボタンで, 押すと (キーボードでは Enter か空白, タッチでは触ると) 説明が印の下 (窓の下端で足りなければ上) に浮いて開き (表の行の高さと列の幅を変えないため), もう一度押す, Esc, 外を押す, 印から Tab で離れる (説明の文を押した後に Tab で移る場合も. 開いている間は, フォーカスの行き先が印の外なら閉じる), 他の印を開くと閉じる (画面を流すか上の部分の高さが変わると印に付いて動き, 印が横に流れる表か画面の見える範囲から外れると閉じる. 説明の文を押して選んでも閉じない) (マウスを置かなくても見られ, 開いた説明を 1 つにするため. `title` は使わず, 読み上げは印の名前と開いた説明の 1 回だけにする). テスト用の守る指標の表が無い実験には印を出さない
- 並べ替えと絞り込み: 一覧と比較では評価の列の見出しで並べ替える (値の無い実験は末尾. 初めに押したときは良い順. 並べていない列での並べ替えは捨てる). 並べ替えは一覧と比較のどちらも URL (`sort` と `desc`) に残す (再読み込みと共有で同じ並びにするため). 比較では, 実験を読み終えた後に並べていない列での並べ替えを URL から消す. 一覧では守る指標の印 (落ちた, 保った, 判断できない) で絞り込み, 検索の欄に `<列><比べ方><数>` (`accuracy>=0.9`, `baseline_test:accuracy_diff<0`. 比べ方は `<`, `<=`, `>`, `>=`. 列は `<評価の名前>:<列>` か, 1 つの評価だけにある列なら列の名前だけ) と書くと値で絞り込む (その値の無い実験は外す. 列に当たらない語は文字で絞り込み, そのことを出す)

### パラメータの無いモデルの実験

学習するパラメータの無いモデル (ML-Quest の異常の検知の骨組みの距離に基づく度合い. 中心と精度行列をバッファに持つ) の実験は, 次の 2 つの形で残る. どちらも他の実験と同じ一覧と画面で読み, 何の実験か, 評価, ファイル, ログ, config, 環境は他の実験と同じに出し, 一覧と比較の評価の列 (テスト用の上位 K 件の適合率と PR-AUC) も並べる (自己符号化器の実験と度合いの決め方で比べるため).

- ML-Found の `fit` で残した実験 (ML-Found の docs/DESIGN.md の「11. 更新の手順」のパラメータの無いモデルの扱い): `run.json`, `history.csv`, チェックポイントを他の実験と同じ形で持つので, 他の実験と同じに読む. 状態, エポック, ベスト, 学習時間, 最終の指標は `run.json` と `history.csv` から出し, 一覧の「完了」の絞り込みと分析の画面にも入る. 他の実験との違いは 2 つで, 違いに合わせて出す
    - `history.csv` に `train/` と `lr` の列が無い: 学習曲線は検証の値 (`valid/precision_at_k` と `valid/average_precision` など) だけを出し, 学習率のグラフを出さない (列の名前で読むので, 列の無い分を出さないだけ)
    - `run.json` の `optimizers` が空のリスト: 詳細のモデルのタブの Optimizer と Scheduler の欄に, 学習で更新する重みを持たないので使わないことを出す. config の `optimizer`, `scheduler`, `optimizers` は書いてあっても学習に使わないので, config から補わない (使っていない Optimizer を出さないため. config から補うのは `optimizers` を書かない版の ML-Found の実験だけ)
- `run.json` と `history.csv` を持たない実験 (`Trainer` を使わず, ML-Found の `start_experiment` で記録, 評価, 成果物だけを残した骨組みの実験):
    - 状態は `run.json` の無い実験と同じくログから決めるので, 学習の完了の行が無く「未完了」(不明) になる. エポックは 0, ベスト, 学習時間, 最終の指標は「—」. 学習曲線のタブは, `run.json` と `history.csv` が無く `evaluations/` を持つ実験では, 学習の記録が無い実験であることと, 評価のタブで結果を見ることを出す (学習の途中で止まった実験と見分けるため). 比較の画面の曲線では, 指標の無い実験として名前を出す
    - 次の段階への案内は, 推論の一式 (ML-Inference が読む `inference/inference.yaml`) を持てば出す (骨組みは評価と成果物を書いた後に一式を作るので, 一式があれば度合いを数え終えている). 状態の表示は「未完了」のままで, 案内を出すかの判定だけで完了として扱う. `inference/` の下に別のファイルだけがある実験 (途中で止まった一式づくりなど) は, 登録できないので一式とみなさない
- どちらの形も, モデルの定義の記録が無く推論の一式を持てば, 次の段階への案内は「実験の一覧から登録」だけ

### 実験のモデルの定義

実験がどのモデルの定義で学習したかは, `source.yaml` の `model_spec` (定義の場所 `path` と中身の `sha256`) から決め, 実験の一覧と詳細に「定義の名前」として返す (候補のモデルを並べて起動した実験を, 比較の画面で定義ごとに分けるため).

- 元の定義の場所: `path` がプロジェクトの `models/` などの定義を指す実験はその場所. 写しから起動し直した実験 (`path` が他の実験の `model_spec.yaml`. 下の「10. 学習の起動」の見分け方) は, `path` が指す実験の `source.yaml` の `model_spec` を辿り, `sha256` が同じ間は元の場所を引き継ぐ (ML-Found の記録は写しの場所になるが, 辿れば元の定義の場所が分かるため. ダッシュボードの置き場に別の記録を持たないので, ダッシュボードの外で起動し直した実験も同じに読める)
    - 辿るのは, 同じ一覧を作るときに読んだそのプロジェクトの実験の中だけ (`path` から実験の ID を作り, 読んだ `source.yaml` の辞書で引く. ファイルを直接開かない). 通った実験を覚え, 同じ実験に 2 度来るか 10 回を超えたら打ち切る
    - 辿った先の実験が無い (消した), `sha256` が違う, 打ち切った場合は「元の定義が分からない写し」とする. 写しの記録が無い (`status` が `copied` でない) 実験の `path` が写しを指す場合も, 中身を比べられないので同じとする
    - 写しと見なすのは, 名前が `model_spec.yaml` で, 読んだ実験のディレクトリか, 出力先から `<名前>/<日付>/<時刻>/model_spec.yaml` の形 (消した実験) にある場所だけ (プロジェクトの `models/model_spec.yaml` のような定義は普通の定義として名前を付ける)
    - 辿った結果は覚えず, 一覧を作るたびに全ての実験の `source.yaml` の辞書から求める (他の実験を消すか書き換えると変わるため). 詳細の画面も, 同じくプロジェクトの全ての実験の `source.yaml` だけを読んで求める (他のファイルは読まない)
- 定義の名前: 元の定義の場所の, `models/` からの相対の場所から拡張子を除いたもの (`models/resnet_small.yaml` は `resnet_small`, `models/a/net.yaml` は `a/net`). `models/` の外の定義はプロジェクトからの相対の場所 (外なら絶対の場所) から拡張子を除いたもの. 他の実験や定義の有る無しで変わらない形にする (一覧, 比較, 検索, 候補の一覧で同じ定義に同じ名前を付けるため). 元の定義が分からない写しは `写し`
- 中身の違い: 名前と一緒に元の場所と `sha256` (写した中身の分かる実験だけ) を返す. 比較の画面が組を分ける鍵は「元の場所 + `sha256`」で, 名前は表示だけに使う (`net.yaml` と `net.yml`, `models/` の外の同じ相対の場所, `写し` という名前の定義が同じ名前になるため). 同じ名前の組が 2 つ以上あれば, 表示の名前に場所か `sha256` の先頭 8 文字を添えて見分ける (定義を書き換えた前後を 1 つに数えないため. 違いの無い組は名前だけで読みやすくするため). `sha256` の無い実験 (写しの記録が無い) は, 元の場所だけを鍵にした別の組にし, 中身の分からないことを添える. 元の定義が分からない写しは, `sha256` ごとの組にする
- `model_spec` が無いか, 写しの記録が無い (`status` が `copied` でない) 実験は, `path` があれば同じく場所から名前を決め (中身が分からないので `sha256` は無い), `path` も無ければ定義の名前を持たない (表では空, 比較では「定義の記録が無い」の組にまとめる)

### 学習曲線の横軸

強化学習や長さの違う学習では, エポックで並べても進み具合を比べにくい (エポックあたりの環境のステップ数やサンプルの数が実験ごとに違う). そこで学習曲線と比較の横軸は, エポックのほかに `history.csv` の他の列から選べる.

- 候補はエポックと, `history.csv` の列のうち, 名前に `/` が無く, 学習率 (`lr`, `lr_<名前>`) と指標 (`train/` など) でなく, 2 エポック以上の全てのエポックに値があり, エポックごとに必ず増える列 (環境のステップ数, 見たサンプルの数など. ML-Found では `step` が `extra` で返した値がこの形の列になる). バックエンドが選び, `GET <run>/history` の `x_columns` で返す. 値だけで選ぶので, 経った時間のような増え続ける列も候補に出る
- 途中で減るか同じ値が続く列 (途中で止まる KL の重みなど) は進み具合に使えないので除く. ML-Found は進み具合の列の名前を決めていない (強化学習の `ml_found.rl` も) ので, 名前ではなく値で選ぶ
- 候補がエポックだけの実験 (比較では, 全ての実験がそうの場合) は, 横軸を選ぶ欄を出さない
- 他の列を選んだ場合は, その列そのもののグラフを出さない (横軸と同じ値の直線になるため). ベストと Early Stopping の目印は, そのエポックの列の値の位置に置く (再開で同じエポックの行が重なる場合は最後の行). 選んだ列の値が無いエポックの目印は出さない (位置が決まらないため). 更新ごとの学習率 (`lr_steps.csv`) はエポックの軸の上の位置なので重ねず, そのことを出す
- 横軸の目盛りは, 選んだ列の値が全て整数なら整数だけにする. 値が全て 0 以上の列は 0 から描く (学習を始めた時点からの進み具合として読むため)

### 強化学習の実験

ML-Found の強化学習 (`ml_found.rl`) の実験も, 同じ実験のディレクトリの形で残る. 指標 (`reward`, `length`, `violations`, `success`. 学習では `loss` と `entropy` も) は `history.csv` のただの指標なので, 学習曲線, 比較, ハイパーパラメータの分析に他の指標と同じく出る. 監視する指標は `valid/reward` で向きは `max` (ML-Found の docs/DESIGN.md の「強化学習」) なので, ベストのエポックも他の実験と同じく `run.json` から読む.

方策の一式 (`policy/policy.json`. ML-Found の `docs/FORMAT.md` の「方策の一式」) がある実験には, 実験の詳細に「方策」のタブを出す.

- 読むのは ML-Found の `read_policy_spec` (版と形を確かめる). 形の決まりを 2 か所に持たないため. 知らない版 (新しい版と版の無いもの), 空間と守りの知らない項目, 壊れた JSON は, 守りを読み違えないように中身を出さず, 読めない理由だけを出す (他の任意のファイルと違い, 読める項目だけを出すことはしない)
- 出すもの: 版, 出力の読み方 (`head`), モデルのクラスの名前, 書き出した時刻, 外れたときの動き (`stop`, `handover`, 決めた行動), 観測の空間と止める条件 (要素ごとの下限と上限), 行動の空間と行動の範囲 (`box` は要素ごとの下限と上限, `discrete` は行動の番号ごとに選んでよいか), 補足 (`metadata`). null は「制限なし」. 要素の多い空間は先頭の 200 個だけを表にし, そのことを出す
- 重みの sha256: `policy/policy.pt` の sha256 を求めて `weights_sha256` と比べ, 「一致」「違う (読む側は読まない)」「重みが無い」を出す. 同じファイル (大きさと更新の時刻) は計算を覚えておく. シンボリックリンクの重みは読まず「重みが無い」とする
- 重みは配らない. 方策のタブにダウンロードのリンクを置かず, 方策の一式を持つ実験では, ファイルを返す API が `policy/` の中のファイル (`policy.json` を除く) と全てのチェックポイント (`.pt` など. ML-Found の `Trainer` で学習するので `final_model.pt` も方策と同じ重み) を返さない (ファイルの一覧には名前と大きさだけを出す). 場所はリンクを辿った先のパスで比べる. 方策を使うかを画面の外で人が決めるため. 方策の一式の無い実験のチェックポイントは返す
- 守り付きの評価の割合: ML-Found の `evaluate_policy` の行を `save_evaluation` で残した表 (上の決め方で `kind` が `table` になる (評価のタブで表として出る) 評価で, 列に `end` と守りの結果ごとの数 `ok`, `clipped`, `fallback`, `stop`, `handover` を全て持つ評価) から, バックエンドがエピソードの数, 終え方 (`end`) ごとの数と割合, 守りが止めたか元の制御に戻したエピソード (`end` が `stop` か `handover`) の数と割合を数えて返す (`policy_outcomes`. 評価と同じ順). 評価のタブに返す行は先頭の 2000 行だけなので, 割合はファイルの全ての行から求める. 終え方は `terminated`, `truncated`, `max_steps`, `stop`, `handover` の順で, 知らない値と値の無い行は「その他」(`other`) にまとめる (ML-Found に終え方が増えても数え落とさないため). 行の無い評価は割合を返さない. 読み方と出さない評価は上の `evaluations/` の読み方と同じ
    - 応答の欄 (`policy_outcomes` の 1 つ): `name`, `split`, `description`, `epoch` (評価のファイルの値. 無ければ null), `episodes` (エピソードの数 = 行の数), `ends` (終え方ごとの `end`, `count`, `ratio`. 上の順で, `other` は 1 行以上ある時だけ), `guarded` (`end` が `stop` か `handover` のエピソードの数), `guarded_ratio` (その割合). 割合は 0 から 1 の数で, エピソードが無ければ null
- 方策のタブには, 守りの表の前に「評価の終え方と成功の割合」を出す. 評価ごとに名前, 分割, エポック, エピソードの数, 説明, 守りが止めたか元の制御に戻した割合 (数も添える), 終え方ごとの数と割合 (百分率で小数 1 桁) の表 (狭い幅でも表の見出しは折らず, 表を横に流す). 守り付きの評価が無ければ, 無いことと `evaluate_policy` の行を `save_evaluation` で残すと出ることを出す. 行の無い評価は割合を出せないことを出す. 学習の指標の成功の割合 (`history.csv` の `valid/success`) があれば, ベストのエポックと値のある最後のエポックの値を並べ (評価の割合と見比べるため), ベストのエポックに値が無ければそのことを, 列が無いか値が無ければ無いことを出す (行を黙って消さないため). 方策の一式が読めない実験は, 守りを読み違えないように一式の理由だけを出し, 割合も出さない
- タブの先頭に「実機での実行は道具の外. 方策を使ってよいか (配備) と守りの範囲は人が確かめて承認する」と出す. ダッシュボードは方策を動かさない

### 記録した軌跡からの方策の見積もり

評価の軌跡の表 (`trajectories/<名前>.csv`. ML-Found の `docs/FORMAT.md` の「trajectories」) がある実験には, 実験の詳細に「軌跡」のタブを出し, 記録した経験から環境で動かさずに別の方策の良さを見る (ML-Found の `estimate_policy_value`).

- 一覧: `/results` の `trajectories` に, 名前の決まり (評価と同じ) に合う `*.csv` を名前の順に並べ, 説明の主な項目 (記録した評価, 環境, エポック, エピソードと行の数, 全てのエピソードが入ったか, 確率の列があるか, 行動の空間) と, 見積もれない理由 (`reason`) を返す. 説明は FORMAT の読む側の決まり (リンク, 普通でないファイル, 1 MiB (ML-Found の公開の `MAX_TRAJECTORY_INFO_BYTES`) を超える説明を読まない. 版が 1 以上の整数でない説明は無いものとする. 新しい版は読める項目を使い知らせる) で直接読む
- 見積もれない軌跡: 記録した方策が行動を選んだ確率の列 (`action_prob`) の無い軌跡 (重みが決まらない), 行動の空間が Discrete でないか行動の列が `action` の 1 つでない軌跡 (決まった形の方策の確率を作れない), 説明の無い表 (行動の空間が分からない), リンクの表. 一覧と見積もりの API の両方で, 同じ理由を返して断る
- 見積もる方策: 行動の空間 `[start, start + n)` の, 一様 (ε = 1) と, 記録で最も多い行動 (同じ数なら小さい値) の ε-greedy (ε / n に, その行動だけ 1 - ε を足す). 空間の外の行動の確率は 0. 最も多い行動は, 表の読み方を 2 か所に持たないため, `estimate_policy_value` に行動を数える関数を渡して数える (この 1 回目の結果は使わない). 記録した方策と同じ方策は作らない (`target_prob` に記録の確率が渡らないため). 比べには記録の方策の平均 (`behavior_value`) を使う.
- 応答 (`PolicyEstimate`): 見積もった方策 (`policy`, `epsilon`, `gamma`, 行動の空間, 最も多い行動 `best_action`) と, `estimate_policy_value` の `value`, `ordinary`, `per_decision`, `behavior_value`, `episodes`, `steps`, `effective_sample_size`, `max_weight_share`, `zero_weight_episodes`, `underflow_episodes`, `low_ess`, `notes`. 有限でない値は null. 有効なサンプルの数がエピソードの数に比べて少なく見積もりが当てにならないかは, ML-Found の結果の `low_ess` をそのまま返す (決め方を 2 か所に持たないため). ML-Found が見積もりを止めた誤り (壊れた表など) は 422 と ML-Found の文
- 画面: 軌跡, 見積もる方策, ε (ε-greedy だけ), 割引率 γ を選び, 「見積もる」を押したときだけ求める (表を全て読むため). 重み付きの重点サンプリングの値, 有効なサンプルの数とエピソードの数, 最も大きい重みの割合, 重みが 0 のエピソード, 3 つの見積もりと記録の方策の平均の表, ML-Found の知らせ (`notes`) を出す. 画面の言葉は日本語にし, ML-Found の関数と項目の名前は出さない. 行動の空間は「0 から 1 の 2 個」のように書く. 有効なサンプルの数が少ないとき, 全ての重みが 0 で重み付きの重点サンプリングの値が決まらないとき, ε = 0 で記録で最も多い行動の他をとったエピソードの重みが 0 になったときは, 知らせの文を出す (ε = 0 を選んだときも先に知らせる)
- ML-Found (と PyTorch) は, 起動のときでなく, 軌跡のある実験を初めて開いたときに読み込む (他の任意のファイルと同じ)

## 10. 学習の起動

- プロジェクトの学習のスクリプトを, プロジェクトの Python で `--experiment <config>` を付けて別のプロセスとして起動する
    - ML-Found のプロジェクトは `train.py --experiment` の形で動かす前提で作られているため
    - ダッシュボードとプロジェクトで Python の環境を分けられる
- プロジェクトの Python は, 登録のとき (と, 場所を移して前の Python が使えないとき) に, プロジェクトに関係する仮想環境から選ぶ. 探す範囲は, プロジェクトが git のリポジトリ (`.git` のディレクトリかファイルを持つディレクトリ) の中にあれば, プロジェクトのディレクトリからそのルートまで. ホームか `/` の手前までにルートが無ければ, プロジェクトのディレクトリだけ. 範囲の中を近い方から, `.venv` と `venv` の `bin/python` の順に探し, 無ければダッシュボード自身の Python (上の階層の関係ない仮想環境 (ホームの近くの別の作業の環境など) で学習を動かさないため. 同じリポジトリのルートの環境 (ML_tester の `.venv` など) は使う)
- 画面で config を書き換えた場合は, ダッシュボードのデータの置き場に config を書き出して渡す. プロジェクトのファイルは変更しない
- 起動の前に, ML-Found の `load_config` と確認の関数 (`start_experiment` が出力先を作る前に行うものと同じ) で config の誤りを確かめる
    - 計算の精度と勾配の蓄積の値の誤り (`fp16` や 0 など) と組み合わせの誤り (closure を使う Optimizer や `optimizers` と勾配の蓄積など) は `check_trainer_config` で誤りにする. `bf16` を学習のデバイスで使えるかは, `get_device(experiment.device)` のデバイスが cpu の場合だけ `check_precision` が小さな計算を実際に行って確かめ, 使えなければ値の誤りにする (フォームで fp32 に戻せるように, config は返す). cuda と mps では確かめは実際に GPU で計算するので, サーバーが GPU の文脈を持ち続けないように, 起動した学習のプロセス (ML-Found が出力先を作る前) に任せる. 使えない場合は, 学習がすぐに誤りで終わる. `trainer.init_weights.path` を書いた config は `check_init_weights` で, ファイルがあり重みの辞書として読めるかを確かめる (中のテンソルは読まない)
    - 確認の結果は, 誤り (起動できない), 注意 (学習のスクリプトが補えば起動できるもの, 学習率が下がりきらないなど), お知らせ (ML-Found が学習を始めるときに補う値など. OneCycleLR の総ステップ数と, `auto` と書いた引数 (`CosineAnnealingLR` の `T_max` など) は学習全体のステップ数, warmup がある場合はその後の残り. 割合で書いた warmup を回数に直すことも知らせる) に分ける. フォームの数の欄にも `auto` と書ける (書けない引数に書くと, ML-Found の確認で値の誤りになる). `optimizers` の場合は, 誤り, 注意, お知らせに `optimizers.<名前>:` を付けてどの Optimizer のものかを示す
- 学習に使う config (default と合わせたもの) のうち, 項目の名前の最後の語 (`_` か `-` で区切った語. 大文字と小文字は区別しない) が `path`, `dir`, `file` で, 値が空でない文字列のもの (`train_path`, `cache_dir` など. `profile` のような語の一部は対象外)は, そのファイルやディレクトリがあるかを確かめ, 無ければ注意にする (データのパスの書き誤りを起動の前に見つけるため. 学習のスクリプトが作るものもあるので, 誤りにはしない)
    - 相対パスはプロジェクトのディレクトリから辿る. ML-Found は自分で使わない項目のパスを読まないが, `experiment.output_dir`, `trainer.resume_from`, `trainer.init_weights.path` を同じくプロジェクトのディレクトリから辿り, ダッシュボードも学習をプロジェクトのディレクトリで起動するため. ダッシュボードは `~` をホームディレクトリに展開して確かめる (展開するかは学習のスクリプトによる)
    - URL (`://` を含む), 値の参照 (`${` を含む), 必須の印 (`???`), Hugging Face のモデルの名前も書ける `name_or_path` で終わる項目 (`model_name_or_path` など), ML-Found が作る `experiment.output_dir`, ML-Found が既に確かめる `trainer.resume_from` と `trainer.init_weights.path` は対象外. リストの中の値も対象外
- 1 つのプロジェクトに学習のスクリプトが複数あり, それぞれ別の default の config を使う場合は (この選び方は ML-Found の `docs/FORMAT.md` の「プロジェクトの形」にも約束として書いてある), スクリプトの本文に書かれた `configs/default/<名前>.yaml` (1 種類だけの場合) を使い, 無ければ名前で選ぶ (`train_<名前>.py` は `configs/default/<名前>.yaml`, 次に `train_<名前>.yaml`, どちらも無ければ `train.yaml`). 本文はパスの文字を探すだけで, 実行はしない. 実験の出力先も, 全ての default の config から集める
- 実験の詳細の「この設定でもう一度起動」は, 実験の `source.yaml` (起動のしかた) から学習の起動の画面を開き, スクリプト, experiment の config, 上書きを入れた状態にする. 状態は URL (`/projects/<ID>/launch?run=<実験の ID>`) に持ち, 再読み込みしても同じ実験から入れ直す. 何を入れるかはバックエンドがまとめて返し, 実験の詳細のボタンも同じ結果で押せるかを決める
    - スクリプトは `source.script` がプロジェクトの学習のスクリプトの一覧にあるもの. 無ければ起動できない理由を出す
    - experiment の config は, `source.experiment` のファイルの今の中身に, 上書き (`overrides`) を ML-Found と同じ規則 (上書きでクラスを変える場合は experiment の引数を捨てる) で重ねたもの. プロジェクトの experiment の config の一覧にあればそれを選んだ状態にし (上書きがあれば, 書き換えた状態), 画面で書き換えて起動した学習 (ダッシュボードの置き場の config) とプロジェクトの `configs/` の中の他の YAML は中身だけを使う. それ以外の場所と, 無くなったファイルは起動できない理由にする. 中身を渡して起動する場合は, 画面からの起動と同じく `experiment.output_dir` を変えたものも起動できない理由にする. 上書きを重ねた場合は YAML を書き直すので, 元のコメントは消える
    - 実験の `diff.yaml` からは作らない. 平坦にした値なので, クラスを変えたときに捨てた引数や, ML-Found が補った値 (`auto` と書いた引数) を元の書き方に戻せないため. その代わり, config のファイルを学習の後に書き換えた場合は今の中身になるので, `source.yaml` より新しいファイルはお知らせする
    - 起動の前の確認には, `source.default` の default の config を使う (スクリプトの本文や名前からは選ばない). 確認と起動の API は default の config を受け取れるが, プロジェクトの `configs/default/` の中の YAML だけを受け付ける. 学習のスクリプトは自分で default を選ぶので, 確認にだけ使う. スクリプトを選び直すと, スクリプトから選ぶ. 起動したジョブにも記録し, 「同じ設定でもう一度」でも同じ default で確かめる (その default が無くなっていれば, スクリプトから選ぶ)
    - モデルの定義: 実験に写した定義 (`source.yaml` の `model_spec`) の `status` が `copied` で, 実験のディレクトリの `model_spec.yaml` (リンクを辿らない普通のファイル, 16 MiB まで) の中身の sha256 が記録の `sha256` と合えば, experiment の config の `model.spec` をその写しの場所 (プロジェクトからの相対パス) に書き換えて入れる (前の実験の後に `models/` の定義を書き換えても, 同じモデルで学習し直すため). ML-Found の約束は写しを「プロジェクトの定義の場所に写す」とするが, ダッシュボードはプロジェクトの定義を上書きしない (今の定義と利用者の書き換えを消さないため). 学習のスクリプトが `model.spec` からモデルを組み立てることは ML-Found の約束 (`model` はプロジェクトの項目) による
    - 写しを使わない場合: 次のどれかに当たる実験は写しを使わず, 今のプロジェクトの定義 (experiment の config の `model.spec`, 無ければ default の config の `model.spec`) から組み立てることと理由をお知らせする. `status` が `copied` でない (知らない値も), 写しが無い, リンク, 普通のファイルでない, 16 MiB を超える, 読めない, 中身が記録と違う. 実験のディレクトリがプロジェクトの外にあるか, 途中にリンクがある (ML-Found が新しい実験に写し直せないため). 場所が `${` を含むか `~` で始まる (config の参照とホームの展開に読まれるため). experiment の config の `model` が辞書でない. 写した定義が外部の重みのファイル (ML-ModelControl の定義のノードの `weights.path`. 部分モデルの中も) を読む (ML-ModelControl は `weights.path` を定義のファイルのディレクトリから辿り, 絶対のパスもそのディレクトリか許したディレクトリの中だけを読むので, 写しの場所からは組み立てられないため). YAML として読めない写し, 入れ子 (辞書と並び) が 100 段を超える写し, YAML の別名 (`&a` と `*a`) を 1 つでも使う写しも使わない (自分を指す別名, 別名を重ねて大きく膨らむ定義, 深い入れ子で長く止まらないため. 別名と深さは読む前の字句の段で数え, 超えたらそこで打ち切る). お知らせには, 今の定義のファイルの sha256 を記録の `sha256` と比べて, 違えば違うモデルになると言い切り, 同じなら定義のファイルが同じ中身であることと外部の重みのファイルは比べていないことを出す (比べられない場合はそう出す). 写しから起動し直した実験の config (`model.spec` が他の実験の `model_spec.yaml` を指す. 名前が `model_spec.yaml` で, `config.yaml` と `source.yaml` を持つディレクトリにあるか, 出力先から `<名前>/<日付>/<時刻>/model_spec.yaml` の形にあるもの (リンクを辿った場所で比べる). 元の実験を消した後も見分け, 出力先が `.` のプロジェクトの自分の定義 (`models/model_spec.yaml`) を取り違えないため) で写しを使わない場合は, `model.spec` を消して default の config の値に戻す (他の実験の写しを確かめずに使わないため). `model_spec` が無い実験 (config に `model.spec` が無いか, `model_spec` を記録しない版の ML-Found で作った実験) は何も足さない
    - 書き換えは上書きと同じく YAML を書き直すので元のコメントは消え, プロジェクトの config を選んだ状態は書き換えた状態になる. 写しを使うお知らせは, YAML の欄の `model.spec` が写しを指す間だけ出し, 「今の定義で起動する」のボタンで `model.spec` だけを今の値 (experiment の config の値. 無ければ項目を消して default の値) に戻せる (上書きなど他の書き換えを残すため)
    - 起動の API は, experiment の config の `model.spec` が実験の `model_spec.yaml` (`config.yaml` と `source.yaml` を持つディレクトリの中) を指していれば, その実験の記録と写しを上と同じく確かめ直し, 使えなければ起動しない (起動の画面を開いた後に写しが書き換わっても, 違う定義で学習しないため. 手で写しを指した config も同じ). 起動しない応答は 400 で, 理由 (`detail`) と `code: model_spec_copy_refused` を返し, 画面は `code` で見分けて次の一手を出す (起動の画面では写しを使うお知らせを「今の定義で起動する」か実験の詳細から開き直す案内に替え, ジョブの画面では「実験を開く」から開き直す案内を足す). 「今の定義で起動する」を押すとエラーの文も消す. ジョブの「同じ設定でもう一度」も同じ API を通るので, 写しを指す config では確かめ直す. 写しを指さない config では今の定義で起動する (実験に写した定義を使うのは, 実験の詳細の「この設定でもう一度起動」だけ)
    - 写しから起動し直した実験は, ML-Found の記録 (`config.yaml`, `diff.yaml`, `source.yaml` の `model_spec.path`) の定義の場所が写しの場所 (`outputs/...`) になる. 元の定義の場所は, 下の「実験のモデルの定義」で写しの記録を辿って求める (元の実験を消すと辿れない)
    - `source.yaml` が無い実験, スクリプトか config の読み込み方が記録されていない実験 (ノートブックや, `load_config` などを使わずに作った config) は, ボタンを押せなくして理由を出す
- 監視する指標と向き: フォームに `trainer.monitor` (文字の欄. 空にすると項目を消し, ML-Found の既定の `valid/loss` か `train/loss` に戻す) と `trainer.mode` (`min` か `max`) の欄を置く
    - 手で書いた名前は, 空白や改行を含めば誤りにして書き込まない (ML-Found の記録の列の名前にならないため). 前の実験の記録の指標の名前 (最後のエポックの値の名前とベストの指標) に無い名前は, 起動を止めずに注意を出す (学習のスクリプトが新しく記録する指標もあるため)
    - 実験が 1 つも無いプロジェクトでは名前を照らさない. 学習のスクリプトが記録する指標の名前は, 学習してみるまで分からないため
    - 問題の設定から値を受け取る欄が働くのは, 骨組みの外のプロジェクト (default の config が `trainer.monitor` を書いていないもの. null も書いていないとみなす) だけ. ML-Quest が書き出す骨組みは default の config に `trainer.monitor` と `trainer.mode` を書くので, 骨組みのプロジェクトには欄を出さない. 骨組みの外のプロジェクトでは, 「問題の設定から」の欄に ML-Pathfinder の問題の設定を並べ, 選ぶとその監視する指標と向き (上の「ML-Pathfinder の問題の設定」) を experiment の config に書く. 渡せない問題の設定は選べなくし, 理由を欄の下に出す. 書いているかは起動の前の確認 (`/validate`) の `monitor_in_default` で返す (default の config の書いたままの値を見る. フォームの config は ML-Found の既定を合わせた値なので, 書いたかが分からないため)
    - そのプロジェクトを記録した (`project.path` が同じ. 両方ともホームを展開してリンクを辿った場所で比べる) 問題の設定があり, 開いたときの config (experiment の config も) が監視する指標を書いていなければ, その値を初めから入れる. config (default か experiment) が `trainer.mode` を書いていれば, 向きは書き換えずに指標だけを入れる (利用者か default が決めた向きのため). 入れるのは config を開くたびに 1 回だけで, 同じ config を書き換えた後や「元に戻す」の後には入れ直さない. config を選び直すと, その config にも入れる. ただし利用者が欄で指標を空にした後は, その画面で config を選び直しても入れない (空にした選択を消さないため). 実験の設定でもう一度起動する場合は入れない (その実験と同じ値で学習するため)
    - 入れた値の出どころとして, 問題の設定の名前と problem.yaml の場所を欄に添える (問題の設定で選んだ指標から決めた値であること). 欄で変えた後は, 問題の設定の値から変えていることと元の値を出す
    - ML-Quest が無い場合は, 問題の設定の値を使えない理由を出し, 監視する指標と向きの欄はそのまま使える
- 骨組みに固有の項目はフォームに欄を置かず, YAML の欄で書き換える. 例えば ML-Quest の並べるの骨組みの `rank` (反応の表の利用者, 品物, 時刻, 反応の強さの列と, 並べる件数 `rank.k`) と `data.valid`, `data.test` (時刻の順に分ける検証用とテスト用の割合). 列の名前は問題の設定の答えなので, 変えるときは ML-Pathfinder で答え直して骨組みを書き出し直す. `rank.k` と割合は, 変えると Recall@K と NDCG の数え方と分割が変わって他の実験と値を比べられなくなるので, 欄を置いて気軽に変えられるようにはしない (変えた実験は一覧の config の差分に出る). ML-Quest の群分けの骨組みの `group` (群を作る列 `group.columns`, 行を見分ける列 `group.id`, 群の数 `group.k`, 安定性の数え方 `group.stability` と回数 `group.repeats` など) も YAML の欄で書き換える. 群の数は比べる実験で変えてよい (群の安定性の評価と config の差分で比べる). 骨組みの config の `requires` (`eda`, `modelcontrol`) は学習の準備で入れ, モデルの定義が無いうちは `model.placeholder: true` の仮のモデルで学習する
- 中断は ML-Found の「中断の要求」(`STOP`) で行う. エポックの区切りで止めるか, `now` でエポックの途中で止める. 利用者が「すぐに止める」を選んだ場合と, 実験のディレクトリがまだ無い場合だけ, プロセスにシグナルを送る (押すたびに SIGINT, SIGTERM, SIGKILL の順に強くする)

### 候補のモデルを並べて起動する

1 つのプロジェクトで, モデルの定義の候補を選び, 同じスクリプトと config で定義ごとに学習して比べる (候補ごとに定義を置き換えて手で起動し, どの実験がどの定義かを覚えずに済むため).

- 候補の一覧: プロジェクトの `models/` の下 (中のディレクトリも) の `*.yaml` と `*.yml` (定義の置き場はプロジェクトの `models/` という利用者の決めに従う). 場所 (プロジェクトからの相対パス), 名前 (上の「実験のモデルの定義」と同じ決め方), 中身の sha256, 大きさを返す
    - 選べないもの (理由を添える): リンク (途中のディレクトリも), 普通でないファイル, 16 MiB を超えるファイル, 読めないファイル, `${` を含むか `~` で始まる場所 (ML-Found が写せないものと, config に書けないものを候補にしないため). `models/` そのものがリンクなら一覧を空にして理由を返す
    - 辿り方: `.` で始まる隠しのファイルとディレクトリを除き, リンクのディレクトリを辿らず (`os.walk` の `followlinks=False`), 辿ったファイルとディレクトリの数にも上限 (5000) を置き, 一覧は 200 個まで (大きなディレクトリで止まらないため)
    - sha256 は, ファイルの (i-node, 大きさ, 更新の時刻) が変わらない間は覚えた値を使う (1000 個まで. 超えたら消えたファイルの分, 次に古い分を捨てる). 中身は ML-ModelControl の形として確かめない (誤りは学習のスクリプトが組み立てるときに分かる. ML-Found と同じ扱い)
- 選び方: 学習の起動の画面の「モデルの定義の候補」の欄で, 一覧から 2 つ以上 20 個まで選ぶ (1 つだけなら普通の起動). default の config に `model.spec` が無いプロジェクトでは欄を出さない (学習のスクリプトが `model.spec` を読まないので, 替えても同じモデルになるため). 欄の上に今の config の `model.spec` を出す
- 候補のまとまりを作る (`POST /api/projects/{project_id}/batches`): 候補ごとに, 今の experiment の config の中身 (書き換えた中身も) の `model.spec` を候補の場所に書き換えた config を作る (書き換えは「この設定でもう一度起動」と同じく YAML を書き直し, `model` が辞書でない config は同じく断る). 全ての候補の config を, 普通の起動と同じ確認 (ML-Found の確認, 追加の依存, 出力先の変更の拒否) に先に通し, 1 つでも誤りがあれば何も起動せず, どの候補の何が誤りかを返す (途中まで学習してから止まらないため)
    - 同じプロジェクトに進めている途中のまとまりがある間は, 新しいまとまりを 409 で断る (候補どうしで GPU を取り合わないため). 候補の確かめの後に, まとまりを作るためのロックの中で確かめ直してから作る (同時に 2 つの要求が来ても 1 つだけ作るため)
    - 書き換えた config は, まとまりの記録 (`batches/<ID>/` の `candidates/<番号>.yaml`) に持つ. ジョブのディレクトリは, 候補を起動するときに作る (待っている候補のために先に作らない. 起動したジョブは, 普通のジョブと同じくジョブのディレクトリに config を写して起動するので, 終わったジョブの「同じ設定でもう一度」もそのまま動く)
    - まとまりの ID は 12 桁の 16 進数で, API はこの形だけを受け付ける (ジョブの ID と同じく, 置き場の外を指さないため)
- 順に学習する: 候補は選んだ順に 1 つずつ, 前の候補のジョブが終わってから次を起動する (同時に動かすと GPU とメモリを取り合い, 学習時間も比べられないため). 前の候補が失敗しても次へ進む (他の候補の結果は比べられるため). 進め方はダッシュボードのプロセスのスレッドが受け持ち, ジョブの状態の確かめ (`JobManager.get`) で終わりを待つ
    - 次の候補は, そのプロジェクトに学習中のジョブ (普通の起動も) が無くなるまで起動しない. まとまりの途中も普通の起動は受け付け (止めない), 学習の起動の画面とまとまりに, 学習中のジョブを待っていることと, 待っているジョブの ID を出す
    - 同じプロジェクトの学習の準備 (環境のジョブ) の間も, 次の候補を起動せずに待つ (入れている途中の環境で学習しないため). 「そのプロジェクトに学習中のジョブと環境のジョブが無いことの確かめ → 起動 (`JobManager.start`)」は, 同じ `launch_lock` の中で行う (確かめた後に普通の起動か環境のジョブが割り込まないため). ロックは「まとまりのロック → `launch_lock` → `JobManager.lock`」の順に取る (取る順をそろえて互いに待ち続けないため)
    - 起動する直前に, 候補の定義の sha256 を読み直し (まとまりを作ったときと違えば, 選んだ後に書き換えた定義なので起動しない), 書き換えた config を普通の起動と同じ確認 (`validate_text`, 追加の依存の確かめ直し) に通し直す. どれかに通らなければ, その候補は「起動できなかった」(理由付き) にして次へ進む
    - 学習を始めた後に, 実験の `source.yaml` の `model_spec.sha256` をまとまりに記録した sha256 と比べ, 違えば (起動の直前から学習を始めるまでに書き換えた場合) 候補に印を付ける
- まとまりの記録 (`batches/<ID>/batch.json`): プロジェクト, スクリプト, 起動の前の確認に使う default, 作った時刻, 持ち主 (ダッシュボードのプロセスの hostname, pid, 起動の時刻), 候補ごとの場所, 名前, sha256, ジョブの ID, 状態, 理由, 印. 状態は, 待つ, 学習中, 終わった, 取りやめた, 起動できなかった. 「終わった」はジョブのプロセスが終わったもの (学習が失敗したものと中断したものも含む. 結果は実験の状態で見る). まとまりは, 待つ候補と学習中の候補が無くなれば終わり. 書き込みは一時ファイルに書いてから置き換える
- 進め方の誤り: 1 つの候補の起動か待つ間に誤り (プロジェクトの登録を外した, 置き場に書けないなど) が起きても進め方を止めず, 次へ進む. 起動する前の候補は「起動できなかった (進め方の誤り: 理由)」, 学習を始めた後の候補は「終わった (終わりを待てなかった: 理由)」にする (ジョブは学習を続けているかもしれないので, 状態はジョブの画面で見る). 進め方が終わるときは (途中で止まった場合も), 残った待つ候補を「取りやめた (進め方が止まったため)」にする (まとまりが進めている途中のまま残り, 新しいまとまりを断り続けないため)
- 取りやめ (`POST /api/batches/{batch_id}/stop`): 待っている候補を「取りやめた」にし, 待っているジョブの記録 (`waiting_for`) を消し, 学習中の候補は普通の中断 (エポックの区切りで止める) をする. 候補のジョブを 1 つ中断しても, まとまりは次の候補へ進む (画面の中断のボタンに添える). 「取りやめていないかの確かめ, 起動, ジョブの ID と状態の保存」と取りやめは, まとまりごとの同じロックの中で行う (取りやめた直後に次の候補が起動しないため). 別のダッシュボードのプロセスが進めているまとまり (持ち主が居る) の取りやめは 409 で断る (ロックはプロセスの中だけなので, 別のプロセスの記録を同時に書き換えないため. 画面はボタンを押せなくして理由を出す). ただし持ち主が「動いて見える」だけで応答しない場合 (置き場を共有した別の hostname が止まった, 確かめられない pid の使い回し) に戻れなくならないため, `force=true` を付けた取りやめは持ち主に関わらず行う. 画面は「持ち主が応答しない場合の取りやめ」として, 持ち主の hostname と pid を出して確かめてから送る. 持ち主が実は動いていた場合は, その持ち主が後で記録を書き換え, 取りやめが上書きされうる (利用者が応答しないと確かめた場合だけ使う前提)
- 記録を消す (`DELETE /api/batches/{batch_id}`): 終わったまとまりの `batches/<ID>/` (記録と候補の config) を消す. 候補のジョブは自分のディレクトリに config を写して起動したので, ジョブの画面, 「同じ設定でもう一度」, 実験はそのまま残る. 古いものを自動では消さない (消したまとまりは画面から比べる入り口が無くなるので, 利用者が選んで消すため). 待つ候補か学習中の候補のあるまとまりは 409 で断る (別のプロセスが進めているまとまりは, そのプロセスが終わりを記録してから消せる). 持ち主の居ないまとまりは, 先に一覧と同じく読み直して (待つ候補を取りやめ, 終わったジョブの候補を終わったにして) 保存してから確かめる. 確かめと削除はまとまりのロックの中で行う (進め方の保存と重ならないため). 置き場の `batches/<ID>` がリンクなら, リンクだけを消す (外を消さないため). 消せなかった場合は 500 と理由を返す
- 取りやめた候補と起動できなかった候補を, まとまりの中で起動し直す手段は持たない (選び直してまとまりを作り直せば同じになり, まとまりの記録を書き換えずに済むため)
- ダッシュボードを起動し直したとき: 持ち主の起動の時刻は, ダッシュボードのプロセスが起動したときに 1 回だけ取った時刻 (タイムゾーン付きの ISO 8601, マイクロ秒まで) とする. 持ち主のプロセスが居ない (同じ hostname で, pid のプロセスが動いていないか, pid が今のプロセスと同じで起動の時刻が違うか, pid のプロセスが持ち主の起動の時刻より後に始まった (pid が使い回された. 始まった時刻は `ps -o lstart=` で秒まで読み, 1 秒の幅を許す. 読めない環境では確かめない. ダッシュボードは起動のたびに新しいプロセスとして始まり, 持ち主の起動の時刻はそのプロセスがモジュールを読んだ時刻なので, プロセスが始まった時刻より後になる. 起動した後に fork したプロセスが進め方を持つ形は前提にしない)) まとまりの待っている候補を「取りやめた (ダッシュボードを止めたため)」にする. 持ち主がこのプロセスでないまとまりは, 持ち主が居るかに関わらず, 一覧を返すときと新しいまとまりを作る前 (進めている途中かの確かめ) に, 学習中の候補を `JobManager.get` で読み直し, ジョブが終わっていれば「終わった」として返す (pid の使い回しで持ち主を見分けられなくても詰まらないため). 持ち主が居なければ, そのときに待つ候補も取りやめにして保存する. 持ち主が居る場合は記録を保存せず, 読み直した結果を返すだけにする (別のプロセスの記録を上書きしないため). 読み直しと保存はまとまりのロックの中で読んでから行う (ジョブは普通のジョブと同じく残る). 別の hostname が持ち主のまとまり (置き場を共有した場合) と, 同じ hostname で動いている別のダッシュボードのプロセスが持ち主のまとまりの待つ候補は, 進め方を持つプロセスが別なので触らず, 画面に持ち主の hostname を出す. ジョブを起動してからまとまりを保存するまでの間に止まった場合は, ジョブだけが残り, まとまりの候補は待つのまま取りやめになることを許す (ジョブの画面には残るため)
- 実験の名前 (`experiment.name`) は替えない (同じ実験の比べ合いなので. 定義の名前で見分ける)
- ハイパーパラメータの分析では, `model.spec` も config の項目の 1 つとして他の項目と同じに扱う (候補の実験では値が定義の場所になり, 定義ごとの結果の違いも見られる)
- 選ぶ: 比べた後は, 比較の画面から選んだ実験の詳細を開き, その実験 (重みを持つ実験のディレクトリと, 写した定義 `model_spec.yaml`) を次の段階 (推論の段階. ML-Inference で推論の一式を作り, ML-Provide で使う) に渡す. ダッシュボードは, 選んだ候補でプロジェクトの default の config の `model.spec` を書き換えない (プロジェクトのファイルはダッシュボードが変えない決まりで, 選んだ定義は実験に写しとして残り, 次の学習の既定を黙って変えないため)
- 既定に戻す: 選んだ候補の定義を次の学習の既定にするには, モデルの作成の画面 (ML-CreateArchitecture) で実験の写し (`model_spec.yaml`) を開き, 名前を付けてプロジェクトの `models/` に保存する (定義を書くのはモデルの作成の画面の役目で, ダッシュボードの決まりは変えない)

## 11. 追加の依存

ML-Found は任意の機能 (`rl`, `mujoco`, `ros2`, `cuda`, 生成の画像の FID の `fid`, 他の段階のライブラリの `eda`, `modelcontrol`, `inference`) に要るものの登録簿を持ち, `describe_requirements()` が機能ごとに, 要るもの (`checks`), 入っているか (`available`), 入れ方 (`install`. pip のコマンド `command` と ML-Found の追加の依存で入れるコマンド `extra_command`, または公式の手順の `url`), 補足 (`note`) を返す (ML-Found の docs/DESIGN.md の「追加の依存」). ダッシュボードはこれをカードで見せ, 足りないまま学習を起動しないようにする.

- **どの Python で確かめるか**: 学習はプロジェクトの Python で動くので, 確かめもプロジェクトの Python の別のプロセスで, 学習と同じ環境変数 (ダッシュボードの `PYTHONPATH` などを引き継がない) で, プロジェクトのディレクトリから `describe_requirements()` を呼ぶ (学習のスクリプトと同じくプロジェクトのディレクトリのモジュールも見つかる). 時間内に終わらなければ, 子のプロセスごと止める. ML-Found の確かめ方はモジュールを import せずに探す (`find_spec`) ので, Gymnasium や MuJoCo を読み込まない (ML-Found 自身と PyTorch は読み込む. `cuda` の確かめに要る). ダッシュボードのプロセスには何も読み込まない
- 結果はプロジェクトの Python とディレクトリごとに 30 秒覚えておく. 同じプロジェクトの確かめは 1 つずつ行い, 待つ間に他の要求が確かめた結果を使う. 画面の「確かめ直す」と学習の起動 (もう一度の起動も) は, 覚えた結果を使わずに確かめ直す. 起動の前の確認 (`/validate`) は覚えた結果を使う (書き換えのたびにプロセスを動かさないため)
- プロジェクトの Python が動かない, ML-Found が無いか `describe_requirements` を持たない版, 時間内に終わらない, 出力が読めない場合は, 確かめられない理由を出す. この場合は起動を止めない (足りなければ学習のスクリプトの `require` が入れ方を示して止まる)
- 入れ方の URL は `http://` か `https://` で始まるものだけを返す
- **版が古い時**: ML-Found は版の下限 (`min_version`) を持つ確かめ方で, 入っている版が下限より古ければ満たしていない (`ok` が `false`) とし, 入っている版 (`version`) を返す. ダッシュボードは確かめ方ごとの `version` と `min_version` を返し (書かない版の ML-Found の結果では null), 満たしていない確かめ方に両方があれば, 「無い」「入っていません」でなく「版が古い」と, 入っている版と下限を出す (入っているのに入れ方を取り違えないため). 書式は全ての所で, 括弧の中を「名前 版, 下限」にし (例: 「版が古い (gymnasium 0.29.1, 1.0 以上が要る)」), 文では「<機能> は入っている版が古いです (…)」と機能の名前を括弧の前に 1 回だけ出す. 機能として版が古いとするのは, 全てが要る (`all`) 機能では満たしていない確かめ方が全て版の古いもの, どれか 1 つ (`any`) の機能では版の古いものが 1 つでもある場合 (それを入れ替えれば満たせるため). 出す所は, 入れ方のカード (見出しの状態と確かめ方ごとの行), 起動を止める文 (入っていない機能と版の古い機能を分けて書く), 起動の画面の見出しと文, 学習の準備の「足りない機能」(版の古い機能は「版が古い機能」に分け, 版と下限を添える. API は `old_versions`). pip のコマンドは版の指定を含むので, 入れ方は入っていない時と同じ. 版を読めない時 (確かめが通り, `error` に確かめていない旨) は今のまま「ある」と出す

### config で要るものを書く

学習に要る機能は, config の一番上の `requires` に機能の名前のリストで書く (例: `requires: [rl]`). default の config に書くとそのプロジェクトの全ての学習に効く. ML-Found は experiment の config に default に無い項目を書けないので, 学習ごとに変える場合は default に `requires: []` などを書き, experiment の config で置き換える (リストは置き換わり, 足し合わない). ML-Found は config の知らない項目を学習に使わないので, 書いても学習は変わらない.

- 学習のスクリプトが `ml_found.rl` を使うかを本文から見分ける方法は選ばなかった. 他のモジュールを通した import や, 機能の名前と import の名前の違い (`cuda` は import ではない) を見落とすうえ, 実行しないと確かでないため. 書いた名前だけを確かめるので, 書き忘れは見つけられない (そのときは学習のスクリプトの `require` が止める)
- `requires` が文字のリストでない (1 つの文字だけも, 書き方の誤りとして直してもらう) か同じ名前が 2 回あれば, config の誤りとして起動しない
- 登録簿に無い名前 (プロジェクトが `register_requirement` で加えるものはダッシュボードから見えない) と, 入っているかを確かめられなかった機能は, 注意にして起動は止めない. `requires` の値の参照 (`${...}`) は学習と同じく解決し, 解決できなければ書き方の誤り
- 足りない機能があれば, 起動の前の確認 (`/validate`) と起動 (`/jobs`, もう一度の起動も) を誤りにし, 次の一手 (pip のコマンドか公式の手順) を文に添える
- 学習の起動の画面は, 選んだ config と書き換えた中身が変わるたびに (少し待ってから) `requires` だけを読む API (`/requires`. ML-Found を読み込まず, default に experiment の YAML を重ねる) を呼び, 足りない機能のカードを開始のボタンの上に出してボタンを押せなくする. 書き換えた中身をまだ確かめていない間もボタンを押せなくする. 確かめられない場合と YAML が読めない場合はボタンを止めない (起動の前の確認と起動が同じ決まりで確かめる)
- 初めて使うときに大きなファイルを取る機能 (今は `fid`. 学習済みの Inception の重み, 約 91 MB) を `requires` に書いた config では, 入っていても, 開始のボタンの上に重みの取得の注意を出す (取る間は学習が止まったように見えるため. ボタンは止めない). 足りない場合は, 出す機能のカードに同じ注意がある

### 追加の依存の画面

プロジェクトの「追加の依存」の画面 (`/projects/<ID>/requirements`) に, 登録簿の全ての機能をカードで並べる. カードは, 入っているか (アイコンと文字. 確かめられない場合はその旨), 説明, 確かめ方ごとの結果, 入れ方 (pip のコマンドとコピーのボタン, ML-Found の追加の依存で入れるコマンド, 説明か公式の手順へのリンク), 補足. 初めて使うときに大きなファイルを取る機能 (`fid`) のカードは, 説明の下に重みの取得 (約 91 MB) の注意を目立たせて出す (補足は ML-Found の `note` のまま). 確かめた Python と時刻, 「確かめ直す」のボタンを添える. 学習の起動の画面と実験の一覧から開ける.

## 12. 学習の準備

問題の設定 (ML-Quest) が書き出したプロジェクトを, 端末を使わずに学習できる状態にするため, プロジェクトの画面の先頭に「学習の準備」のカードを置く. 確かめるのは default の config (`configs/default/train.yaml`) の次の項目.

| 項目 | 確かめ方 |
| --- | --- |
| データセット | `data.dataset` のパスがあるか (ML-EDA が書き出したディレクトリ). 書いていなければ「分からない」とし, 準備を止めない |
| モデルの定義 | `model.spec` を書いた場合だけ, そのパスがあるか. `model.placeholder: true` (定義のファイルが無いうちは学習のスクリプトが仮のモデルで学習することの目印. ML-Quest のファイルの組の骨組みが書く) があれば, 無くても (場所を空の文字にした場合も) 準備を止めず, 知らせるだけにする (書き出した直後でも学習を確かめられるため. 目印は真偽の `true` だけを読む) |
| 学習の環境 | 入れる先の Python があるか, その Python で ML-Found を読み込めるか, `requires` の機能が入っているか (上の「11. 追加の依存」と同じ確かめ) |

- パスは学習と同じく, 値の参照 (`${...}`) を解決し, 相対パスはプロジェクトのディレクトリから辿り, `~` はホームに展開する. 解決できない値は理由を出す
- **入れる先の Python**: 登録した Python がプロジェクトの `.venv` の中か, ダッシュボード自身の Python (登録のときに仮想環境が見つからなかったもの) なら, プロジェクトの `.venv/bin/python`. 利用者が選んだ他の環境 (上の階層の仮想環境など) はその Python で, `.venv` は作らない
- **環境のジョブ**: 「環境を作る」(`.venv` が無い場合) か「足りないものを入れる」を押すと, 動かすコマンドを見せ, 「実行する」で始める. コマンドは次の順
    1. `.venv` が無ければ作る. uv があれば `uv venv --seed --python <ダッシュボードの Python> .venv` (端末からも pip を使えるように pip を入れる), 無ければ `<ダッシュボードの Python> -m venv .venv`
    2. 入れるものがあれば, uv なら `uv pip install --python <入れる先の Python> ...`, 無ければ `<入れる先の Python> -m pip install ...`. ML-Found が無い (か確かめられない) 環境には, ML-Found と `requires` の pip で入る機能を全て入れる. ML-Found がある環境には, 足りない機能だけを入れる. 入れるものの指定は ML-Found の `environment_packages` から作る (ML-Found は git の main. プロジェクトが ML-Found を submodule (`ML-Found/`) で持つ場合は, 固定した版を使うようにそれを `-e` で入れる)
    3. 環境の ML-Found の登録簿に `requires` の名前が無い (古い版) 場合は, ML-Found だけを入れ直す (git の main は版の番号が変わらないため. uv は `--reinstall-package ml-found`, pip は `--force-reinstall --no-deps`)
- pip で入らない機能 (`ros2`, `cuda`) は入れず, 公式の手順へのリンクを出す. 登録簿に無い名前 (プロジェクトが `register_requirement` で加えるもの) は入れず, 確かめもしない
- ジョブはダッシュボードのプロセスのスレッドでコマンドを順に動かし, 出力を置き場の `environments/<プロジェクトの ID>/output.log` に残す. 失敗したコマンドで止まる. 1 つのプロジェクトで同時に動かせるのは 1 つで, 動いている間はそのプロジェクトの学習を起動しない (起動ともう一度の起動は 409. 入れている途中の環境で学習しないため). 逆に, そのプロジェクトの学習が動いている間は環境のジョブを始めない (409. 動いている学習のパッケージを入れ替えないため). 学習の起動はジョブを作った後にもう一度確かめ, 環境のジョブが動いていれば作ったジョブのディレクトリを消して 409 を返す. 学習の起動の確かめ直しと起動, 環境のジョブの開始の確かめ (学習が動いていないこと) と始める印は, 1 つの共有のロックの中で行う (入れ違いで両方が始まらないようにするため. 環境のジョブの時間のかかる確かめはロックの外). 時間の上限は置かない (PyTorch などの大きなパッケージを取るため). 学習と同じ環境変数 (ダッシュボードの `VIRTUAL_ENV`, `PYTHONPATH` を引き継がない) で, プロジェクトのディレクトリから動かす
- 終わったら, 入れる先がプロジェクトの `.venv` なら, 登録したプロジェクトの学習に使う Python をその `.venv` に付け替える (入れるものが無く付け替えだけが要る場合は, 「.venv を使う」のボタンで付け替えだけをする). 確かめた結果の覚えを捨て, カードを確かめ直す
- ダッシュボードを起動し直すと, 動いていたジョブは見届けられないので「途中で止まった」と出す (コマンドのプロセスはダッシュボードと一緒に止まる)
- 全てがそろう (データセットがあるか書いていない, モデルの定義を書いていればあるか仮のモデルの目印がある, 環境に ML-Found と `requires` の機能が入っていて, 学習に使う Python が入れる先と同じ) と「学習を始める準備ができています」と出す

## 14. 課題の型への広げ方

課題の型ごとの出力の形 (何の実験か `task.yaml`, データ全体の評価 `evaluations/`, 見本 `samples/`, 方策の一式 `policy/`) は ML-Found に足し, この画面はそれを ML-Found の関数で読んで見せる (上の「9. 実験の読み込み」). 型ごとの見せ方 (見本の種類, 方策の守り) は, ML-Found の約束に項目が入ってから足す.
